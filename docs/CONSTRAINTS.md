# Engineering constraints and tripwires

*Level 3 of the documentation (**Understand**), a maintainers' record. Index and concept → evidence map: [`understand/README.md`](understand/README.md). The user contract is [`V1_CONTRACT.md`](V1_CONTRACT.md).*

The accumulated record of the constraints the code is held to, kept by maintainers. It began as the constraints written for the first tracer (the first section below, "MUST" / "MUST NOT", predates `src/`) and has grown one block per later decision. It is an engineering artifact, **not the user contract**: the reader-facing statement of what VALANCE guarantees is [`V1_CONTRACT.md`](V1_CONTRACT.md), and the chronological investigation record is [`FINDINGS.md`](FINDINGS.md).

Each line is either enforced by a tripwire (`packages/valance/test/boundaries.test.ts`, `examples/tracer-web/test/*`, `examples/tracer-web/browser/*`) or listed as "reviewed only". Numbering is historical and is not tidied, because tests, comments and findings cite it: blocks are not in numeric order and C20 is used twice (the second, "C20, trigger and scope", clarifies the first). Later blocks refine earlier ones; where two disagree, the later and `V1_CONTRACT.md` win.

## MUST

1. **C1, one composition boundary.** An application author defines and starts a *Valance* application; they do not wire a NEXUS host to a PORT. *(tripwire: tracer example imports no `Mesh.host`/`createWebPort`.)*
2. **C2, substrate ownership.** Behavior is NEXUS's (`Application.start`, state, commands), render semantics are MESH's (`Mesh.host`, render-v1), realization is PORT's (`draw/update/hydrate`). Valance calls them; it reimplements none. *(reviewed + render tripwire)*
3. **C3, real paths only.** The tracer runs the real compiler, MESH runtime (WASM), NEXUS 0.11 and port-web.
4. **C4, target independence.** The core entry (`.`) names no Web type and imports no PORT package. Target specifics live in the `./web` subpaths. *(tripwire)*
5. **C5, substrates stay independent.** MESH and PORT never depend on Valance or NEXUS; Valance's core depends on NEXUS and on the MESH runtime package's public operations (its types and `declaredEvents`). It never depends on the MESH compiler (build time only) or on any program representation: it asks MESH about a program and never reads one. *(tripwire)*
6. **C6, explicit lifecycle.** `start` creates the application; the *caller's Scope* owns its lifetime; `start` is where platform is supplied; Valance owns render/update orchestration (a fiber and a target, both finalized by the Scope, target first); shutdown is scope close or `Application.shutdown`. The start boundary: one `start` is one application lifetime for one caller Scope, and it returns the handle only when the state exists and commands are admitted (ready for `state`, `invoke`, `mount`, `hydrate` and `Web.history`); it does no presentation, URL or consumer work. A failed start gives a typed `StartError` and no handle (an invalid initial state: `InitialValueInvalid`; a platform that fails to initialize: `ServiceGraphFailed`), so nothing can be admitted or committed; what it had already acquired belongs to the caller's Scope and is released when that Scope closes (no rollback machinery, no restart). A caller Scope that is already closed, or that closes while the platform is still starting, cannot produce a live application: `start` dies with the runtime's terminal defect (`NEXUS: the runtime has begun terminating`), whatever the platform acquired is released, and the close settles cleanly. Two applications are two `start`s over two Scopes and share nothing. The handle is that application's identity: `state`, `invoke`, every mount and every history made from it refer to its one lifetime, state, command registry and state stream (mounts and histories from one handle share the application and keep their own presentation or listener state), no operation reaches another application and no global current-application exists, an unknown key is `UnmappedCommand` per application, closing one application makes only its own admission terminal and alters no other application or its consumers, and attaching a consumer (before or after commits, or with none) never starts or renews anything: a later consumer reads the current state and replays nothing. The command boundary through a handle: a key is resolved in the application's own registry before admission (unknown: the typed `UnmappedCommand`, before and after close, nothing admitted or run); a known command's input is validated by its schema before its body is entered (invalid or missing input: the typed `CommandValidationError`, the body never runs, nothing commits) and the body receives the decoded value; a command commits only through the state it is given, and a commit is authoritative whatever the command does afterwards (fail before committing: no commit; commit then typed failure or defect: the commit stays and `invoke` reports the failure in its own channel, typed failure, defect and interruption staying distinct); a command's failure is never an application lifecycle event (the application keeps admitting, other commands and consumers are affected only by a commit that actually happened); commands overlap (C33) and complete independently of presentation (zero consumers is fine, and completing implies no mount has presented the result). The state mutation boundary under it: the application's one state cell is the only owner, and a command is the mutation path (mounts and histories observe; attaching and presenting commit nothing, nothing flows from a presentation back into state, and history's only way in is the configured navigate command). `State.set` validates its value against the schema first (invalid: the typed `StateValidationFailed`, no commit; valid: the decoded value commits); `State.update` is the trusted writer, atomic (concurrent updates all land), committing nothing when its function fails and committing a returned value as is, WITHOUT validation (an invalid-by-schema value returned by an update becomes the authoritative state, which `set` would have refused). Every commit is one element of `State.values`, authoritative whether or not any consumer presents it; after the application's close nothing commits through any path (a known key meets the terminal refusal, an unknown one stays the typed `UnmappedCommand`) and the last state stays readable; a command on one application never touches another's state. Observation is four separate things, none a second owner: a read (`handle.state`) is the authoritative state at that moment, visible as soon as a commit completes (before its stream element is delivered) and creating no subscription or obligation to present; the state stream is asynchronous, begins with the current state (not the history), then carries one element per commit in commit order with nothing fabricated and nothing for a failed mutation, a slow observer lags on its own without delaying commits or other observers, and it ends with the application's Scope (a later observer gets a finished, empty stream) and never resumes; a mount consumes it as a latest-state consumer that may skip superseded elements (C32) and history as another consumer with its own subscription, neither altering the stream or implying the other has seen a state; independent applications have independent reads and streams. NEXUS's `Selector` is not part of VALANCE's public surface (`ApplicationHandle` is `state` and `invoke`), so no derived observation is a VALANCE contract. Capabilities and resources (NEXUS's mechanism, nothing added by VALANCE): a resource the platform supplies belongs to one application's Scope: it is acquired by `start` (not by first use), held across command completions, mount closes and history closes, and released exactly once when the application's Scope closes; a command resolves only its own application's implementation (two applications, two implementations, no sharing however their commands interleave), and neither a mount, a history nor any observation (reads, the state stream, presentation) acquires, uses, owns or releases it. A capability failure is the command's own typed failure, never an application lifecycle event: before a commit it commits nothing, after one the commit stays (the command boundary above); consumers stay alive and the application stays usable. After the close admission is terminal, so no capability operation runs and nothing commits. Startup resources and command-time capabilities are one mechanism (the platform Layer, acquired at start, used by commands through `Capability.require`) under one rule: the caller-owned application Scope. *(tripwire: lifecycle + J1 isolation, `test/application-start-boundary.test.ts`, `test/application-handle-composition.test.ts`)*
7. **C7, program continuity and drawn render stay with the composer** (PORT CONTRACT; NEXUS M1/M2). Valance dispatches each event with the render whose tree is drawn, never a newer one. *(tripwire)*

## MUST NOT

- No router, plugin system, CLI, dev server, platform registry, diagnostics framework, optimizer.
- No second hydration protocol: `hydrate` is PORT's; Valance only decides *when* to call it.
- No `any`; no `ApplicationDefinition.environment` / `CapabilitySource`.
- No application code mutating the target. The only path to the target is state → render → PORT.
- No compat shims. (None were needed; if one appears it is documented in `FINDINGS.md`.)

## Added for stage 2 (written before the multi-view code)

- **C8.** One `Valance.start` per application, however many MESH programs it shows; route state lives in application state; the active program is derived from it.
- **C9.** A program change is PORT's `draw` (continuity is the composer's fact); Valance never asks PORT to `update` across programs.
- No `@valancex/router`, route DSL, navigation registry, or route lifecycle; no second application to simulate navigation.

## Added for stage 3 (URL ↔ application state; written before the code)

- **C10.** Still one `Valance.start`, one state, one platform lifetime. The URL is derived from, and feeds, application `path`; it is never a second source of truth.
- **C11.** Browser Back/Forward enters application behavior through the SAME navigate command a MESH intent uses. No second navigation pathway.
- **C12.** MESH and PORT do not change. NEXUS changes only if the tracer proves a missing primitive.
- No Router/Route/route DSL/registry/guards/loaders/redirects/outlets/parameters/wildcards; exact-path comparison only. *(A destination link primitive was added in 0.5.0: see C39.)*

## Added for stage 4 (URL shape; written before the code)

- **C13.** URL ≠ state. What a URL means is application code (`urlOf`, `stateOf` in the example app). `Web.history` reads and writes the URL and calls them; it parses nothing.
- **C14.** Same navigate command, same single application. No Router, codec, mapper, normalization, or public `urlOf`/`stateOf` API.

## Added for stage 5 (initial URL canonicalization; written before the code)

- **C15.** Starting an application never creates a history entry because `Web.history` saw a representation mismatch.
- **C16.** Interpreting the initial URL (`stateOf`, total) is not synchronization (`urlOf`, later commits). Which one owns canonicalization is decided by evidence, not assumed; no public `replaceState`/canonicalization API unless a stable need is shown.

## Added for stage 6 (the guard; written before the code)

- **C17.** `Web.history` answers "did the application's URL change?" (`urlOf(state)` vs the last synchronized `urlOf`), not "does the browser URL equal the application's?". It is not a canonicalizer.
- **C18.** Starting writes nothing, popstate never writes, and the signature and public surface of `Web.history` do not change.

## Added for stage 7 (stabilization)

- **C19.** The `Web.history` contract is tested at unit level (`packages/valance/test/history.test.ts`); Chromium stays the acceptance check. No new options, API, rollback or resynchronization.

## Added for stage 29 (command lifetime; adopted from the Stage 27/28 evidence)

*The lifecycle (application, mount, event command, ledger) is stated for readers in `docs/V1_CONTRACT.md` (sections 6, 7 and 9); `docs/FINDINGS.md`, "Canonical lifecycle architecture", is its evidence trail. C20 to C26 are its invariants.*

- **C20, command lifetime (safety).** A command admitted through the application's command boundary (`inApplication`, reached by both `ApplicationHandle.invoke` and MESH dispatch) remains owned by the application until it exits. When draining begins (the caller's Scope closes), VALANCE closes admission and interrupts and awaits every already-admitted command BEFORE NEXUS terminates and platform resources release. *(tripwire: `examples/tracer-web/test/capability-async.test.ts`, "the VALANCE command-lifetime contract")*
- **C21, admission during drain.** No new command is admitted after draining begins; the refusal is a defect (`VALANCE: admission is closed (draining)`). The check and the registration are one synchronous step. *(tripwire: same)*
- **C22, ownership boundary.** The registry owns commands, not application fibers: daemon and escaped fibers are outside it; structured children are covered by their command. It is internal: `ApplicationHandle` exposes no lifecycle, drain, shutdown or registry. NEXUS, MESH and PORT are unchanged.
- **C20, trigger and scope (Stage 30, clarifies C20).** "Draining begins" means the caller's Scope closing, the only route in the VALANCE model. The drain constrains admission and the lifetime of admitted commands; it does not forbid state changes by commands that are still running (Stage 30, Interpretation A). `Application.shutdown(running.nexus)`, reachable only through `./internal`, is the substrate's early end: it does not pass the drain and the contract is not claimed for it.
- **C23, liveness limitation (documented, not solved).** An uninterruptible admitted command that depends on a NEW admission can keep shutdown from completing; the application stays alive and its resources are not released under the command. No timeout, forced interruption, watchdog or fallback admission. *(tripwire: contract 5)*
- **C25, event commands (Stage 39).** A command admitted from a mount's event is the application's, exactly like an invoked one: it remains owned by the application until it exits. Closing the mount that reported the event ends that mount's follower and target, not the command; the application's close interrupts it through the registry (C20 to C22). The mount remains the source: its ledger (`Mounted.dispatched`) records the exit, even after it closed. *(tripwire: `test/event-ownership.test.ts`, `browser/event-lifetime.browser.test.ts`)*

## Added for stage 38 (mount lifetime)

- **C24, a mount's lifetime is the caller's Scope's.** `mount`/`hydrate` end with the Scope the caller supplies (target and follower finalized by it, target first), and relate to the application's Scope in no other way. The application ending ends the mount's follower, not its target. An independent mount may therefore outlive its application as a drawn, inert target until its own Scope closes. This is permitted, not an error. The lifetime matrix: the application's Scope A (runtime, state, command admission), a mount's Scope M (its follower and target) and a history's Scope H (its listener and follower) are caller-owned and none is a child of another; each close ends exactly what that Scope owns. Closing M or H never closes or interrupts A or any other mount or history, and the application may live with none (it commits with no presentation and no history work); closing A closes neither M nor H (mounts end inert, a history keeps its listener and refuses popstate, C30/C31/C33), and each of them still closes independently at its own boundary afterwards; no close creates an application lifetime or a commit; a fresh mount or history while A lives starts from the current state, after A closed a mount is refused and a history attaches inert (C30, C33); A closing racing M closing breaks neither boundary (no presentation after M's close resolved, no commit after A's). No unified lifecycle manager, implicit Scope or automatic teardown exists. *(tripwire: `browser/mount-lifetime.browser.test.ts`, `test/scope-topology.test.ts`, `test/cross-scope-lifetime.test.ts`)*

## Added for stage 40/41 (the event-exit ledger)

- **C26, the event-exit ledger is a mount-owned diagnostic observation facility.** `Mounted.dispatched` is append-only (settle order, never removed or reordered), belongs to the mount that dispatched, keeps receiving exits after that mount's target closed until its commands have exited, and lives as long as `Mounted` is held. It is not application state, is not exposed by `ApplicationHandle`, is read by nothing in Valance, and is not part of the application programming model. `Mounted.settled` is a barrier over an open mount's own held dispatches, does not read the ledger, and on a closed mount returns at once. *(tripwire: `packages/valance/test/entry.test.ts` (the handle is `{state, invoke}`: `packages/valance/test/entry.test.ts`), `browser/event-ledger.browser.test.ts`)* Every dispatch outcome (success, the command's typed failure, its defect, interruption) settles the dispatch, is recorded as itself in the ledger, releases `settled`, and commits only what the command actually committed. The mount's held dispatches are released by `settled` or by the mount's close (even if the target's `unmount` throws); a `settled` already waiting when the mount closes keeps waiting for the dispatches it had captured and ends when they exit (at the latest the application's drain), and never waits for later ones. An inert mount keeps its last good render for events (C31): an event on it dispatches, commits, is recorded and covered like any other.

## Added for the navigation boundary (probes in `examples/tracer-web/test/history-boundary.test.ts`)

- **C27, the navigate key is the application's, not Valance's.** `"app/navigate"` appears in no Valance source: it is the name of one binding in the application's table, and `HistoryOptions.navigate` is how history is told it. MESH intents, `invoke` and popstate reach that one binding, so there is one semantic entry point. Valance does not know the command's argument shape: it passes `stateOf(url)` through unread.
- **C28, history fails closed and logs.** A popstate whose navigate key is unbound (`UnmappedCommand`), whose argument the command rejects (`CommandValidationError`), or whose `urlOf`/`stateOf` throws, changes no state and writes no URL; the failure is logged (`Effect.logError`), never returned (`history` has no error channel), and later navigation still synchronizes. Browser URL and application state may then differ until the next application navigation; restoring one is the application's policy. Invariant added: a defect in the application's `urlOf` or `stateOf` never ends the history follower. The navigate key is an `app/...` entry, not a declared event, so C34's conformance check does not cover it: an application whose history names an unbound navigate key still starts, and a popstate that reaches it fails closed as above.
- Whether every committed view transition must be realized, or may be coalesced: decided by C32 (a mount may skip superseded intermediates).

## Added for multi-mount semantics (`examples/tracer-web/test/multi-mount-views.test.ts`)

- **C29, one application, N mounted presentations.** A started application has one NEXUS runtime, state, resource lifetime and `view(state)`; each mount owns only a target, the render it drew, and its own draw/update continuity. The view is the application's, so every mount shows the same one (there is no per-mount view); a report is dispatched against its own mount's drawn render; closing a mount ends that presentation and nothing of the application; application resources are released by the application's Scope, after every mount that shares it.

## Added for lifecycle ownership (`examples/tracer-web/test/lifecycle-ownership.test.ts`)

- **C30, every binding lives in the Scope it was given.** Like a mount (C24), `Web.history` owns its listener and follower through its own Scope, related to the application's only by what the caller passes. In a shared Scope it ends before the application; in its own Scope it outlives the application, still listening until that Scope closes: a popstate is attempted through the application's navigate entry, refused by the closed application, logged (C28), and writes nothing; the application keeps no usable command path. A history attached later (after another closed, or after the application navigated with none attached) takes the CURRENT state as its baseline and writes nothing: it synchronizes later transitions, and a navigation made while none was attached is never added to the browser's history. Attachment across the application's close: while the application lives, and while it drains (the runtime is still alive; only an already admitted command can commit then), `Web.history` attaches and follows as above; after the application's Scope has closed it still attaches (it never fails to attach, unlike `mount`/`hydrate`, C33) and installs its listener, but the state stream is over, so it takes no baseline, writes no URL, commits nothing and renews nothing: a popstate is attempted through the application's navigate entry, refused by the closed application and logged (`popstate navigation failed`), contained in history's follower, each time and for every history attached, until that history's own Scope closes and removes the listener (after which nothing is synchronized or logged, and the application is untouched either way). `handle.state` stays readable throughout. A closed mount leaves its container empty and the container takes a new mount; mount and hydrate are per-mount choices. Two live mounts on one container are not a supported arrangement (PORT promises no container exclusivity, and Valance does not know containers).

## Added for the inert mount (`examples/tracer-web/browser/inert-mount.browser.test.ts`)

- **C31, a mount that stops following is inert, not unmounted.** Whatever ends a mount's follower (the application ending (C24), an invalid MESH render, a failing PORT target) leaves its target drawn with the last good render, retained for events, until that mount's own Scope closes; `followed` says why. The application stays authoritative and keeps committing, nothing recovers by itself, other mounts and fresh mounts are unaffected (a fresh mount renders the current state), and closing the inert mount disposes only it. What the retained render means for an event: it resolves against THAT render (its handler identity, intent and arguments), never against the view the application has since selected, and the resulting command runs against current application state (a retained event only invokes an application command, which stays authoritative); the mount presents nothing and never resumes because an event changed state, another mount's presentations never replace its retained render, a fresh mount (even in the same container) starts from current state with a normal first draw, and after the application closes the retained event meets the terminal refusal (C33). The logical commit point of a presentation is the return of the target's `draw`/`update`/`hydrate` (a hydration PORT handles, adopted or drawn afresh on a mismatch, is a successful presentation; only a throw is a failure): only then does the render become the mount's retained one, so a target operation that throws (before or after it changed the physical target) leaves the PREVIOUS render retained, the mount inert, and no presentation of the new render recorded; events keep resolving against the previous render, even when the physical target now shows more (a handler only in the new render is refused, one only in the previous render still resolves). Partial physical effects of a throwing operation belong to PORT: no rollback, no reconciliation between the retained render and the physical target. A first `draw`/`hydrate` that throws gives no `Mounted` and retains nothing (no event from whatever PORT left in the container dispatches, and the failed attempt registers no finalizer, so it is never unmounted); a fresh attempt starts from current state. No staleness check, version or invalidation exists or is implied. Failure ownership with several mounts: the invalid APPLICATION state is shared but a MESH render failure is each mount's own attempt, so every mount that actually renders it fails independently with the same diagnostic, while a mount that skips it (C32) does not fail because another rendered it, and may go on to present the final valid state; a target failure is local to its mount and fails no other; a mount already inert keeps its own cause and is never failed again by another mount's failure; repairing the state revives no inert mount, a fresh mount draws the repaired current state, and commits never wait for any mount (there is no mount-level validity gate and no cross-mount failure propagation). A presentation failure is local to the mount that has it, whatever else is happening: the application keeps admitting and committing (nothing waits for a failing or inert mount, and there is no application-wide presentation-failure state or error channel), the state stream and `Web.history` keep delivering and following every commit, other mounts keep presenting at their own pace on their own retained renders, a target failure and a MESH failure each end only the follower that met them, an inert mount's events still resolve against its retained render and the current state without resuming it, and recovery is only a fresh mount on the current state. Closing the application is the other class: it ends every mount's follower, but asynchronously, and it linearizes application STATE, not presentation. Nothing commits after `Scope.close` resolves; the mounts' followers belong to their own Scopes (C24), are not awaited, and consume what the stream had already delivered: a presentation begun before the close finishes (target operations are synchronous, so the retained render follows the operation's return with no point for a close to land between them, for a first draw or hydrate, an update and a view-changing draw alike), and the latest state committed before the close may still be rendered and presented after `Scope.close` resolved (at most that one, never a state beyond the last commit), after which the follower ends inert. No presentation admission is gated on the application's close, and nothing here adds one; a mount's own Scope close is the awaited boundary (nothing is presented after it resolves, C33). The owner of the cause differs, the effect does not: an invalid render comes from the state, so every mount that renders that state ends (a mount may skip a superseded invalid state, C32); a target failure ends only its own mount.

## Added for bursty commits (`examples/tracer-web/browser/burst.browser.test.ts`)

- **C32, a mount presents committed state in commit order and may skip superseded intermediate states.** Application state is authoritative and independent of presentation: every command commits, `State.values` carries every commit, and a slow or failing mount never delays a commit. A mount's presentations start from the state current when it begins following and converge on the latest committed state. Each one is rendered from the latest state available when the mount reaches it, so a state superseded before then is skipped; what is presented is never reordered, repeated or invented, and a state already presented is not presented again. Continuity is relative to the render actually presented: a view other than the drawn one is a `draw`, the same view an `update`, even when a skipped intermediate was another view (so DOM-resident state such as focus survives a skipped round trip and is lost by a presented one). An event is dispatched against the render its mount currently has drawn, whatever has committed since. Mounts consume independently: they may skip different intermediates and converge on the same latest state. Not guaranteed: that every committed state is presented, how many are, or when; which are skipped; that an invalid-render intermediate is rendered (its MESH diagnostic exists only if that state is rendered, C31), though an invalid LATEST state fails the mount; latency, fairness or main-thread responsiveness. History is unaffected: `Web.history` follows committed states in its own subscription (C17). Pacing is the caller's: an application or host that cares about input latency issues commits across macrotasks through the public API (awaiting `invoke`, or an application command that sleeps between commits), and a mount's work then follows the commit rate; Valance neither paces nor yields. Presentation is the boundary: VALANCE's retained render is what VALANCE and PORT successfully presented, not a continuously observed snapshot of the physical target. External changes to the realized DOM are neither detected, reconciled nor reported (nothing rerenders and nothing fails because the DOM differs from the render); the next update is requested from the application's state transition and applied by PORT against its own record, a view change is a normal draw, events resolve through the retained render (never through DOM labels or metadata; an element PORT did not create is simply unreachable), a commit after the realized DOM was removed still gets its normal update with no redraw or recovery, and unmount clears the container wholesale. Continuity is decided by view identity alone, never by the render's structure: a same-view change in what MESH renders (a conditional appearing or disappearing, keyed repeat members added, removed or reordered) is one `update` from the render actually presented, whatever intermediates were skipped, and two different views that render structurally identical output are a `draw`; VALANCE neither inspects nor compares render trees, and what an `update` does with the structure (which realized nodes are kept, created or removed) is MESH identity and PORT realization, not guaranteed here. A same-view structural change that MESH cannot render ends the mount as any invalid render does (C31), and an event afterwards resolves against the newly presented render, so a removed node has no dispatch path. VALANCE has no render-equality or no-op presentation semantics: every state that reaches a mount is presented, an `update` for the same view and a `draw` for another, even when the render is unchanged (state outside the render, an equal-valued but distinct state, a repeat, an unchanged tree whose event arguments changed, or two views with output-equivalent renders), and the presented render, not its tree, becomes the retained one that events resolve against. The only state a mount does not present again is the very state object it last read (reference identity: no structural state equality, no render comparison). That is distinct from skipping a superseded state under C32. Concurrent commits change none of this: commit → `State.values` → wake-up → state read → render → presentation is not a serialized queue. Every commit is authoritative and the stream delivers each one, a mount reads the latest state when it reaches presentation (not the state that woke it), so it presents an increasing subset of the committed sequence ending at the latest (it may skip superseded commits, never reorders or invents a state, and a commit landing during a presentation is seen by the next one after the started presentation completes), continuity stays relative to what it actually presented, mounts pace independently and may present different subsets, a mount that skips an invalid intermediate does not fail where one that rendered it does (C31), and `Web.history` is another consumer of `states` that sees every commit whatever any mount presents. These moments are not one-to-one with commits and have no total order across them beyond what each consumer observes. The retained render is the sole logical source of interaction identity and arguments: it is exactly the render of the mount's last SUCCESSFUL presentation (a failed update never replaces it, a draw for another view replaces it, and a draw back never reuses the older render of the original view), an interaction dispatches against it whatever the current application state, the physical DOM or another mount holds, and so two mounts may carry different arguments for the same event site. The retained render is read once, synchronously, when the target reports the interaction: from then on its handler identity, intent and arguments are fixed, and no later presentation (a successful update or draw, a failed one, another mount's) or state commit changes them; the command, by contrast, runs against the application state it finds when it executes, so presentation-derived interaction data and execution-time application state are captured at different moments. After the report, admission and lifecycle are the application's (C20, C26, C33): closing the mount does not stop an admitted command (its exit still reaches that mount's `dispatched`), closing the application interrupts it, and an interaction reported after the application closed is refused. Admission is part of the report, not of the command's start: the dispatch's own fiber registers itself with the application as its first step, in the same synchronous run as the report, and only then does MESH resolve the handler (inside the admitted fiber) and the bound command start, so an interaction reported before the application's admission closes is admitted (and a drain may interrupt it before it ever executes), one reported after is refused before MESH looks at its handler (with the refusal of C33: an unmapped command is then not reported as `UnmappedCommand`, unlike `invoke` with an unknown key, which is looked up before admission), and closing a mount's Scope is not an admission boundary. What is guaranteed is only the boundary: report, admission, execution, commit and completion are separate moments, interactions from one or several mounts keep their own render-derived arguments, and each command's execution, commit and exit follow its own progress (the exits reach `dispatched` in settle order, not report order), with no promised ordering across commands; the caller's exit of an uninterruptible command that committed during a drain is still `Interrupted` (C33). No event version, snapshot or staleness check exists. Whether MESH or PORT do any work for an unchanged tree is theirs and not a VALANCE guarantee. Once a mount's first presentation has succeeded, how it was established (`mount`'s draw or `hydrate`) is not a VALANCE concept: both retain the same kind of render and share one continuity model (same view an `update`, another view a `draw`, events against the mount's own retained render, a later failure an inert mount, application state the only baseline), and a fresh mount in a container that once held a hydrated one is an ordinary draw of the current state. What the physical target keeps from hydration is PORT's, with no VALANCE guarantee. Physical integrity of the target after a successful draw or update belongs to PORT and to whoever else touches that DOM. The cost of one presentation belongs to MESH's synchronous `render` and the target's synchronous `draw`/`update` (PORT's `void` operations, with no completion signal): Valance holds no partially realized render and has no meaningful split point, and asynchronous or incremental realization would be an upstream MESH/PORT contract change that nothing currently requires.

## Added for lifecycle races (`examples/tracer-web/test/lifecycle-races.test.ts`)

- **C33, closing an owner never lets a stale callback commit, and in-flight work belongs to the Scope that owns it.** Closing the application's Scope: no commit follows the close (a commit racing it either happened or is refused), the state stays readable (`handle.state` is the last committed state) and equals exactly the commits that happened, mounts end inert (their followers end asynchronously: a state committed before the close may still be presented after it resolved, C31), and every later `invoke`, mount event or popstate is refused the same way: `invoke` is a lazy Effect that DIES (a defect, not a typed failure) with `NEXUS: the runtime has begun terminating`, or with `VALANCE: admission is closed (draining)` while the drain runs; an unknown key is still the typed `UnmappedCommand`. A command admitted before the close is interrupted by the drain (it commits only if it already had), unless it is uninterruptible (C23): then `Scope.close` waits, the commit happens before it resolves, and the command's caller still sees `Interrupted`, so the state is the record of whether it committed. With several admitted commands only the boundary is contractual: every commit precedes `Scope.close`'s resolution and the state is exactly the commits that happened. How they interleave inside the drain is not promised: the drain currently interrupts them one at a time, in admission order, awaiting each one's actual exit, so an uninterruptible command can delay the interruption of one admitted after it, which may then still commit during the drain and report success; commits follow each command's own progress, and a caller sees success or `Interrupted` according to whether the drain reached its command first. Admission is decided when the Effect runs, not when `invoke` is called (every run after the drain began is refused). Admitted commands run concurrently, each in its own fiber, with no VALANCE queue, lock, transaction or staleness check: two commands may both read the same prior state, a commit is visible to any command that reads after it (whether or not the committing command has exited), and what they can rely on is only what NEXUS's state primitive gives, `State.update` as one atomic read-modify-write (concurrent updates all land), while a separate read followed by a write that ignores the current value is the command's own read-then-write and can overwrite another's commit. Commands are application-owned writers that VALANCE neither inspects nor merges; admission order, start order, read order, commit order, completion order and the order of exits in a mount's ledger are separate and unspecified (each follows the command's own progress), and the only ordering guarantee is the close boundary above. Closing a mount's Scope: a presentation pending for it is dropped, nothing is presented after its unmount, a stale callback on its old target reports nothing, and an event command already admitted is the application's (C25) and still commits, its exit recorded in that mount's ledger. Closing a mount's or a history's Scope is likewise a clean boundary for that resource's own activity: target operations and `pushState` are synchronous, so nothing is suspended inside one when a Scope closes; the follower is interrupted and awaited, and no draw, update, unmount, history write or follower-made navigation follows the close's resolution. If the target's `unmount` throws, that is the target's own defect: `Scope.close` fails with it (the other finalizers in the Scope, such as the application's, still run), `unmount` was called exactly once and a second close does nothing, `followed` is unchanged, other mounts and the application are untouched, and the mount's own bookkeeping still happens (it releases its held dispatches, so `settled` on a closed mount returns at once, C26). A popstate navigation in flight when history closes is interrupted with the follower (it is an `invoke`), unlike a mount's admitted event command, which the application owns (C25). A lifecycle operation never stays pending only because its caller-owned Scope is closed: `mount` and `hydrate` into a Scope that is already closed, or that closes before the follower starts, end with the interruption (nothing is drawn, no target operation), exactly as when the Scope closes during their start; `Web.history` into a closed Scope returns with no listener. A first render that fails ends `mount`/`hydrate` with its own cause, never a hang and not disguised as interruption: MESH's typed diagnostics for an invalid render, the target's defect for a throwing first `draw`/`hydrate`; when the Scope's close happens at the same moment either may win. A hydration mismatch is not a failure (the tree is drawn afresh and `hydration` says why). A failed attempt registers nothing and leaves no follower or target activity, so a fresh attempt on a repaired state succeeds. A mount or history attached afterwards starts from the current authoritative state. That holds while the application lives, including while it drains (the runtime is still alive: a mount or hydrate draws the current state and follows, and its follower ends when the close completes). Once the application's Scope has closed nothing can be mounted: `mount` and `hydrate` end with the defect `the application ended before its first render` (the state stream is over, so no first element ever arrives): no render, no target operation (the container, or the server markup a hydrate was given, is untouched), no finalizer, no commit and no restart, while `handle.state` stays readable as the last committed state. `invoke`, `mount` and `hydrate` after the close are all refused with defects of their own (different messages, never a typed error; an unknown `invoke` key stays the typed `UnmappedCommand`). A mount can recover a mount (a fresh one on the current state) but cannot renew the application's lifetime, which is only the Scope `start` was given.

## Added for start conformance (`packages/valance/test/conformance.test.ts`)

- **C34, a started application's declared events all have command-table keys (`D ⊆ B`).** `start` returns a handle only if the programs of EVERY view pass MESH's program-level checks and every `component/command` key MESH reports as declared (unselected views, inactive conditional branches and repeated bodies included; duplicates are one requirement) is an own key of the table `commands(state)` returned. VALANCE obtains D from MESH (`declaredEvents`) and never parses a program (C5). A program MESH rejects fails `start` with MESH's diagnostics first, and `D ⊆ B` is then not evaluated; diagnostics that depend on the values a scope produces stay render-time. A violation is the typed `ConformanceViolation`, listing every missing declaration (view, component, event, command, key, MESH's span) in view order and then MESH's order. Extra table keys are permitted: `B ⊆ D` is not required. The check is of key presence only: it says nothing about a NEXUS command, a binding's command, arguments, schemas or success. There is no bypass, flag or report-and-continue mode. `UnmappedCommand` remains the runtime defense below `start` (broader than D: undeclared keys, history's key, a render from another application's programs). *(tripwire: `conformance.test.ts`; the unmapped-command path is exercised below the boundary in `dispatch-admission` F)*

## Added for application-owned async work, start-time work and application-lifetime resources

*Tripwires: `examples/tracer-web/test/application-owned-async.test.ts`, `application-start-work.test.ts`, `server-start-work.test.ts`, `application-scoped-capability.test.ts`. Stated for readers in `V1_CONTRACT.md` §18.*

- **C35, start-time work is an admitted command with no caller.** `ApplicationDefinition.start` is a key of the command table. `start` admits that command through the registry of C20, once, with no arguments, as its last step (after every check; a failed `start` runs nothing). It is the application's from admission: it needs no caller Scope, closing the application's Scope interrupts and awaits it before NEXUS terminates, a close racing `start` either interrupts it or leaves it unrun, and it never commits after the close resolves. A key the table lacks fails `start` with the typed `UnmappedCommand`. Its exit is returned nowhere; a failure it does not catch is **logged** (`Effect.logError`, "start-time work failed", as C28 logs a failed popstate), and interruption (the application closing) and a refusal by a closing application are not logged; no startup error channel, hook, second key or skip option exists. *(Tripwire: `application-start-work.test.ts`.)*
- **C36, `renderToHtml` begins start-time work and does not await it.** It is `start` plus one render, so the work begins and is interrupted when the render ends. The returned `state` is read after the render and can be newer than the `html` when the work commits in between. Today's behavior, characterized and not a design requirement. *(Tripwire: `server-start-work.test.ts`.)*
- **C37, an application-lifetime resource is not a command-scoped one.** A resource acquired in a command's own scope is released when the command ends. One that must live as long as the application is owned by the platform's Scope (acquired at start, or later through a platform capability that runs scoped acquisitions into it). VALANCE exposes no application Scope; it adds no resource registry. Such a resource is released once at termination, after the drain, in reverse order; an acquire interrupted by the drain holds nothing, and a default (uninterruptible) acquire holds the close open (C23). *(Tripwire: `application-scoped-capability.test.ts`.)*

## Added for name-keyed commands (`examples/tracer-web/test/name-keyed-commands.test.ts`)

- **C38, a bare command name is an identity, not a global behavior.** In the table `commands(state)` returns, a key without `/` holds a NEXUS command and is bound to every declared `component/name` with that name and to `app/name`; a key with `/` is an exact binding. For each of those keys the exact entry wins over the bare name; there is no other precedence. The table `start` uses (conformance, hosts, `invoke`, `start`) is the one plain table of exact keys built from both forms and D, so `D ⊆ B` (C34), admission and the registry are unchanged. A bare command's struct input takes arguments in field order; a non-struct input takes the first argument; a binding under a bare name is a startup defect. `define` reads the table's own type: `E` is the exact union of every command's failure plus `CommandValidationError` (a table of bare commands carries it nowhere else), and `R` the union of the services the table needs, so commands that fail differently share one table with no failure widened (tripwire: `packages/valance/test/command-errors.test.ts`). A table built by spreading another definition's `commands(state)` loses the spread-in members from `E` (TypeScript drops the index signature of a spread `CommandTable`): that gap is older than this rule and is not fixed by it.


## Added for the 0.5.0 interface (`packages/valance/test/{links,history,history-navigate,manifest,payload,waiting}.test.ts`, `examples/tracer-web/browser/{links,docs-field}.browser.test.ts`)

- **C39, a link is a destination, not a handler.** `Web.link` is an `<a href>`; the application never writes an event for it. `Web.history({ container })` handles a link click only when it is a plain primary click on a same-origin anchor; a modified click, `target`, `download`, a foreign origin, a `#fragment` and a prevented click are left to the browser. Still no Router, route table or guard: what a URL means is `urlOf` / `stateOf` (C13).
- **C40, the MESH manifest is derived, never written.** `manifest({ primitives, scopes, commands })` (from `@valancex/valance/web/build`) derives it from the tags, each view's scope Schema and the command table. A hand-written manifest is not a supported path for ordinary authoring.
- **C41, a text field shows the rendered value.** `Web.textField` (`controlled("value")`) writes the DOM property after every presentation, only when it differs, and never moves a focused caret otherwise; its `input` event carries the typed string. This needs PORT Web 0.3.0.
- **C42, `waiting` is a NEXUS command, scoped.** `command(state).waiting` adds no concept to the model: latest-wins per command, `wanted` required and evaluated atomically with the commit, a superseded run is not cancelled, interruption is not failure, a failure is passed as received. Typed failures and several effects stay with the general NEXUS form.
- **C43, a bare `navigate` name receives the navigation fact as the command's whole input.** An exact key behaves as before; the positional rule for events and `invoke` is untouched (C38).
- **C44, the document title is the application's function.** `history.titleOf` sets `document.title` for the first state and every later one, after the URL step; the server writes the same function's result. A view cannot carry a `<title>`.
