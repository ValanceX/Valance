# VALANCE v0.2 release notes

## v0.2.0

*Released 2026-10-04 (`v0.2.0`).* The second release of `@valancex/valance`. It keeps the 0.1.0 public entries and `ApplicationHandle` (`{ state, invoke }`), changes the presentation contract to latest-state (below), fixes four lifecycle and history edge cases, and ships the reader-facing contract, [`docs/V1_CONTRACT.md`](../V1_CONTRACT.md). It changes nothing in NEXUS, MESH or PORT. The package is still pre-1.0: the API can still change.

| `@valancex/valance` | **0.2.0** | the commit this tag will point at |

The ranges are unchanged from 0.1.0. Installation, with explicit ranges, is in [`docs/V1_CONTRACT.md`](../V1_CONTRACT.md) section 13 and the package README. Each package keeps its own version.

### Behavior changes since 0.1.0

- **Latest-state presentation.** A mount presents committed state as a latest-state consumer: a woken follower reads the current state and may skip superseded intermediate states, and a state it already presented is not presented again. Application commits are authoritative and never wait for a mount. This replaces the 0.1.0 behavior in which every commit was rendered in turn; statements in `docs/FINDINGS.md` that say otherwise are historical.
- **`mount` / `hydrate` settle instead of hanging.** Into a Scope that is already closed, or that closes before the follower starts, they end with the Scope's interruption.
- **A throwing `unmount`** no longer leaves a closed mount holding its dispatches: `Scope.close` fails with the target's defect, but VALANCE's own bookkeeping is released, so `settled` on a closed mount returns at once.
- **`Web.history`** logs a defect in the application's `urlOf` or `stateOf` and ends only that synchronization step, instead of ending the follower.

### Contract and documentation

- `docs/V1_CONTRACT.md` is the reader-facing contract. `docs/CONSTRAINTS.md` remains the engineering constraints and tripwires (extended with the lifecycle, command, state, observation and capability boundaries), and `docs/FINDINGS.md` the historical investigation record.
- Capability and resource ownership (acquired by `start`, held across consumer closes, released once with the application's Scope, never reached after close) is established and tested; it needed no code change.

### Validation

Measured on the commit before the version change; the release preparation changed only version metadata and documentation.

- Package unit tests: 34 passed (5 files).
- Workspace jsdom tests: 414 passed (57 files).
- Chromium (`pnpm test:browser`): 47 passed (17 files), over 12 consecutive full runs including shuffled file order. One browser test was changed for isolation (a probe left a forward entry in the shared session history); no product change.
- A strict pnpm external consumer, outside the workspace, installed the packed tarball with the documented explicit ranges; its typecheck, build and Node/jsdom run (start, mount, a click, `invoke`, server rendering) passed with no undeclared imports and one NEXUS and one `effect` copy.
- Typecheck and build clean.
- The built-page smoke tests and the real-bfcache test were not part of this validation.

### Not in this release (still unproven, by design)

A second PORT, a real asynchronous browser capability, data that ages, long-lived pages, several mounts in a real browser page, browsers other than Chromium, and server-side commands.

### Notes

- Release automation (`.github/workflows/release.yml`) publishes from a tag that equals `v` plus the package version: pushing `v0.2.0` runs all of CI on the tagged commit, packs `@valancex/valance`, publishes it to npm with provenance (it needs the `NPM_ACCESS_TOKEN` secret) and creates the GitHub release with the tarball and these notes (`docs/releases/v0.2.md`). `0.1.0` is already on npm and is not republished.
- The 0.1.0 notes, [`v0.1.md`](v0.1.md), are the historical record of that release.
