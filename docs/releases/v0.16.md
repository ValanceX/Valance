# VALANCE v0.16 release notes

## v0.16.0

*Prepared 2026-10-25 (nothing tagged or published: v0.15.0 is the latest release).* The next minor of the five packages that share one version. Later changes of the release are added below.

### `define` without `view` (Tier 1)

With exactly one entry in `views`, `Valance.define` no longer needs `view`: it is that view, the rule `defineApp` already follows. With more than one entry `view` is still required, and leaving it out is a type error. Additive: a definition that gives `view` is unchanged. Tier 1 (a default for what has only one answer). Audit T1.2 for the Valance column, with A4 (`learn/first-application.md` derives the manifest and now drops `view`): Partial to Pass. Test: `packages/valance/test/define-default-view.test.ts`.

### Stability coverage test (tooling)

`packages/valance/test/stability-coverage.test.ts` fails when a public entry of a published package (`cli`, `common`, `router`, `style`, `valance`, read from each `package.json` `exports`) exports a value `docs/stability.md` does not name; an `./internal` entry is checked only for its row. It found `assetPath` and `withAssets` (`@valancex/common/desktop`), `recording` (`@valancex/common/record`), `request` and `only` (`@valancex/common/http`) and `property` (`@valancex/valance/web`), now named in the stability table. `docs/use/README.md` lists every `ValanceErrorCode`, including `missing-view`. Tooling only, no API change. Audit E3 for the Valance column: Partial to Pass (every value export of a published entry now has a tier, and the test keeps it so).

### `invoke` keys from the table, `command-argument-order`, a typed `resolve` (Tier 1 for `invoke`; tooling)

* **`invoke` names the table's keys.** `ApplicationHandle<S, E, K extends string = string>`: `start` reads `K` from the command table `define` was given (`"app/name"` for a bare command, an exact `"component/name"` key as written), and `invoke`'s key is `K | (string & {})`, so an editor completes the table's keys. Additive: any string is still accepted, and an unknown key is still the typed `UnmappedCommand` at run time. **Typos are not caught by the type**: a table built by spreading another (`{ ...shared(state), own }`) has keys its type does not show, and rejecting them would be a false error. The arguments are not typed per key (they stay `IntentArgument`s). `invoke` is now a method, so a typed handle is still an `ApplicationHandle<S, E>`. Tier 1 (nothing to write). Test: `packages/valance/test/invoke-keys.test.ts`.
* **`vlx check` warns `command-argument-order`** where a template passes a bare command's arguments under names that are not its fields in order (`move(to, "a")` for `Schema.Struct({ from, to })`), where the binding is positional ([Contract §3](../V1_CONTRACT.md#3-state-and-commands)). Narrowed later in this release: a call that names every argument after a field binds by name and is not warned about (see "A bare command binds by name", below). The first warning of the tools: a diagnostic may now carry `"severity": "warning"`, which `vlx check` prints and does not fail on (the VS Code extension shows it as a warning). Test: `packages/cli/test/argument-order.test.ts`. Code documented in the CLI README, "Diagnostics".
* **`resolve` is typed.** `vlx check`, `dev` and `build` write `.valance/types/library-components.d.ts`, the qualified ids (`package/name`) of the library components `src/main.ts` lists, into `@valancex/common`'s new `LibraryComponentIds`; `resolve` takes a `ResolveId`, one of them, and any string while there are none. Written before the compile, so it is there when a collision stops it. Test: in `packages/cli/test/library.test.ts`, "the qualified ids are written as a type".

Audit I2 for the Valance column: the `resolve` id is typed and the `invoke` key is named (completed, not checked). The result for I2 is given once, under "A bare command binds by name", below.

**Upgrading.** Nothing is required: every change here is additive, and code that compiled with 0.15 compiles. For a typed `resolve` in a project made before 0.16, add `".valance/types/*.d.ts"` to `include` in `tsconfig.json` (`vlx init` now writes it).

### `handle.command`: a checked key, a typed input (Tier 1, opt-in)

`ApplicationHandle<S, E, K, C>` gains `command(key, input)`, which runs the same table as `invoke` (the same admission, the same failures) with the key and the input checked by the type. `define` reads `C` from the command table and `start` passes it on, as it does `K`. A bare command's `"app/name"` takes its input whole, typed by its schema: a struct by field name (`handle.command("app/move", { from: "a", to: "b" })`), so no argument depends on its position; another input as itself; nothing for a command that takes none. The input is validated by the command's schema as always. An exact `"component/name"` key takes its entry's arguments, as `invoke` does, because what an `entry`'s adapter makes of them is not in its type. A key the table's type lacks is a type error. A table whose type has no literal keys (annotated as `CommandTable`) takes any string, and an unknown key is the typed `UnmappedCommand` at run time. The limit: a table built by spreading one typed as the wide `CommandTable` has keys its type does not show, and `command` rejects them; give the shared table its own literal keys (no annotation), or call those keys with `invoke`. Additive: `invoke` is unchanged, and the handle's keys are now `state`, `invoke` and `command` (`test/entry.test.ts`). Tier 1 (nothing to write; a typo is caught where it is written). Test: `packages/valance/test/command-keys.test.ts`.

Audit I2 for the Valance column: callers outside a render now have a checked key and a by-name input. The result for I2 is given under "A bare command binds by name", below.

### `Web.run` takes `native` and `target` (Tier 3, Provisional)

* **`native`** is PORT Web's native hatch (north-star refinements B6), handed to the PORT unread: `{ [component]: (element, { key }) => cleanup | void }`, typed by PORT's `@valancex/port-web/native`. The callback gets each drawn element of that primitive once it is in the document (after a draw, an insert, a hydration) and nothing that reports or dispatches; its cleanup runs when the element ends and on `host.stop()`. The PORT writes back the slots it owns on its next write, and only an `opaque` primitive gives the callback its content. A callback for a component the table does not have is refused (`invalid-primitives`), and `Web.run` rejects with it. Needs PORT Web's next release, where the peer range starts (see Upgrading). The type lives in the `./web` entry only: Valance's core names nothing Web (`test/boundaries.test.ts`).
* **`target`** takes the factory `Web.run` builds (`Web.target` with `container`, `primitives` and `native`) and returns the one it mounts or hydrates with, so a wrapper no longer has to give up `Web.run`'s duties (the `Mounted`, the URL policy, `stop`). It is the unprotected hatch: what it writes to DOM the PORT owns is not kept true. `docs/use/platform.md` now shows both, `native` first.

Additive: a `Web.run` call without them is unchanged. Tier 3 (an explicit escape hatch to the platform), Web only, not in contract v1. Test: `examples/todo/test/native-hatch.test.ts` (and PORT Web's own tests of the hatch). Audits for the Valance column: **H1** (a documented way down) ◐ to P: `Web.run` reaches the platform through two named, documented options, `native` constrained by the PORT and `target` marked unprotected (Web only: the desktop host builds its own target, and a desktop parallel waits for evidence, Port ROADMAP §2.8). **H2** (the hatch cannot corrupt framework state) ◐ to P: `native`, the hatch the docs now lead with, gets no report or dispatch, and the PORT re-asserts its slots (tested in PORT). `target` stays unprotected by design and is marked so; the 10-25 validation scored H2 on the weaker documented hatch, and on that reading `target` alone would keep it ◐.

**Upgrading.** Nothing is required for code that does not use `native`. The release raises `@valancex/valance`'s peer range for `@valancex/port-web` (`packages/valance/package.json`) to start at the PORT release with the hatch, so `native` is never silently ignored: install that PORT with 0.16. On this branch, until both are released, PORT Web comes from a local pack (a `DO NOT MERGE BEFORE THE RELEASES` commit), and an older PORT would ignore the option.

### A bare command binds by name where the call site has names (Tier 1; behavior)

MESH's runtime now gives an intent's argument a `name` when it is written as a plain path (`to`, `row.id`; Mesh Task 28). A bare command whose input is a struct binds by it: when **every** argument of the call carries a name, every name is a field of the struct, and no two share one, each argument fills the field of its name (`move(to, from)` for `Schema.Struct({ from, to })` sets `to` and `from` as written). Otherwise the binding is positional as before, and so it is for `invoke` whose arguments carry no `name` (it binds by name when they do), and for a non-struct input.

**Behavior.** The only call that changes is one whose names all match fields but are not in field order: 0.15 filled the first field from the first argument (swapping them, the case `command-argument-order` warned about); now each lands in its own field. A call in field order, a call with a literal or `$event`, and any call with a name that is not a field are unchanged. The `command-argument-order` warning narrows to match: it fires only where the binding is still positional (a name is missing, or is not a field, or repeats) and the names disagree with the field order. The Nexus adapter passes `intent.arguments` through unchanged, so Nexus needs no change. Needs the Mesh runtime with argument names (`@valancex/mesh-runtime` after 0.17.0, where `peerDependencies` should start); with an older runtime no argument has a name and the binding is positional, as in 0.15. Tier 1 (the call site's names are the contract). Audit I2: the Valance column goes Partial to Pass with this (the ecosystem's I2 also needs the refinements' Task 26, Nexus's duplicate-tag refusal, 82bc0ee); events from a template and `handle.command` both bind by name. Tests: `packages/valance/test/named-binding.test.ts`, `packages/cli/test/argument-order.test.ts`.

**Upgrading.** A template written as `move(to, from)` to a command `{ from, to }` and relying on the swap must now write `move(from, to)`, or pass a literal. On this branch, until Mesh releases, the runtime comes from a local pack (a `DO-NOT-MERGE` commit).

### Secrets stay out of the page: `Schema.Redacted` state fields (Tier 1; behavior)

North-star refinements C-3. A state field typed `Schema.Redacted` is never embedded: `renderToHtml` returns `state` without it, and `Web.run` with `present: "hydrate"` starts the browser with the default the field declares. `vlx check` reports two new errors, `redacted-no-default` (a Redacted field with no default) and `redacted-in-view` (a view's `scope` reads one, found by running `scope` on the initial state). `defineApp` keeps a Redacted field out of the layout's scope, so a template that names it is an unknown name. No configuration: authors already mark secrets with `Redacted`. Tier 1 (an existing marker, nothing new to learn). Contract §17 and `learn/mounting-and-hydration.md` no longer say the whole state is embedded. `redactedFields` is new on the `@valancex/valance` entry (Provisional, `docs/stability.md`).

**Not yet:** the `context` projection (Task 19) is not checked; `redacted-in-view` covers `scope` only, and `problemsOf` in `packages/valance/src/web-redacted.ts` is where to add it. The state is decoded as given, so the default of `Schema.Redacted(S)` is the plain encoded value and the default of `Schema.RedactedFromSelf(S)` is a `Redacted`; both work.

**Behavior.** A state that held a Redacted field was embedded as `"<redacted>"`; now the field is absent from the page and restored on hydrate. Audit D2 for the Valance column: Partial to Pass. Tests: `packages/valance/test/redacted.test.ts`, `packages/cli/test/redacted.test.ts`.
