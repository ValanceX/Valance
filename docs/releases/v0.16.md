# VALANCE v0.16 release notes

## v0.16.0

*Prepared 2026-10-25 (nothing tagged or published: v0.15.0 is the latest release).* The next minor of the five packages that share one version. Later changes of the release are added below.

### `define` without `view` (Tier 1)

With exactly one entry in `views`, `Valance.define` no longer needs `view`: it is that view, the rule `defineApp` already follows. With more than one entry `view` is still required, and leaving it out is a type error. Additive: a definition that gives `view` is unchanged. Tier 1 (a default for what has only one answer). Audit T1.2 for the Valance column, with A4 (`learn/first-application.md` derives the manifest and now drops `view`): Partial to Pass. Test: `packages/valance/test/define-default-view.test.ts`.

### Stability coverage test (tooling)

`packages/valance/test/stability-coverage.test.ts` fails when a public entry of a published package (`cli`, `common`, `router`, `style`, `valance`, read from each `package.json` `exports`) exports a value `docs/stability.md` does not name; an `./internal` entry is checked only for its row. It found `assetPath` and `withAssets` (`@valancex/common/desktop`), `recording` (`@valancex/common/record`), `request` and `only` (`@valancex/common/http`) and `property` (`@valancex/valance/web`), now named in the stability table. `docs/use/README.md` lists every `ValanceErrorCode`, including `missing-view`. Tooling only, no API change. Audit E3 for the Valance column: Partial to Pass (every value export of a published entry now has a tier, and the test keeps it so).

### `invoke` keys from the table, `command-argument-order`, a typed `resolve` (Tier 1 for `invoke`; tooling)

* **`invoke` names the table's keys.** `ApplicationHandle<S, E, K extends string = string>`: `start` reads `K` from the command table `define` was given (`"app/name"` for a bare command, an exact `"component/name"` key as written), and `invoke`'s key is `K | (string & {})`, so an editor completes the table's keys. Additive: any string is still accepted, and an unknown key is still the typed `UnmappedCommand` at run time. **Typos are not caught by the type**: a table built by spreading another (`{ ...shared(state), own }`) has keys its type does not show, and rejecting them would be a false error. The arguments are not typed per key (they stay `IntentArgument`s). `invoke` is now a method, so a typed handle is still an `ApplicationHandle<S, E>`. Tier 1 (nothing to write). Test: `packages/valance/test/invoke-keys.test.ts`.
* **`vlx check` warns `command-argument-order`** where a template passes a bare command's arguments under names that are not its fields in order (`move(to, from)` for `Schema.Struct({ from, to })`). The binding stays positional ([Contract §3](../V1_CONTRACT.md#3-state-and-commands)). The first warning of the tools: a diagnostic may now carry `"severity": "warning"`, which `vlx check` prints and does not fail on (the VS Code extension shows it as a warning). Test: `packages/cli/test/argument-order.test.ts`. Code documented in the CLI README, "Diagnostics".
* **`resolve` is typed.** `vlx check`, `dev` and `build` write `.valance/types/library-components.d.ts`, the qualified ids (`package/name`) of the library components `src/main.ts` lists, into `@valancex/common`'s new `LibraryComponentIds`; `resolve` takes a `ResolveId`, one of them, and any string while there are none. Written before the compile, so it is there when a collision stops it. Test: in `packages/cli/test/library.test.ts`, "the qualified ids are written as a type".

Audit I2 for the Valance column: Partial, unchanged. The `resolve` id is typed, the `invoke` key is named (completed, not checked), and the by-position filling of a bare command's input is warned about but stays (the refinements' B4, a Nexus change, is the other half of I2 ◐ to P).

**Upgrading.** Nothing is required: every change here is additive, and code that compiled with 0.15 compiles. For a typed `resolve` in a project made before 0.16, add `".valance/types/*.d.ts"` to `include` in `tsconfig.json` (`vlx init` now writes it).

### `Web.run` takes `native` and `target` (Tier 3, Provisional)

* **`native`** is PORT Web's native hatch (north-star refinements B6), handed to the PORT unread: `{ [component]: (element, { key }) => cleanup | void }`, typed by PORT's `@valancex/port-web/native`. The callback gets each drawn element of that primitive once it is in the document (after a draw, an insert, a hydration) and nothing that reports or dispatches; its cleanup runs when the element ends and on `host.stop()`. The PORT writes back the slots it owns on its next write, and only an `opaque` primitive gives the callback its content. A callback for a component the table does not have is refused (`invalid-primitives`), and `Web.run` rejects with it. Needs PORT Web's next release (an older PORT ignores it). The type lives in the `./web` entry only: Valance's core names nothing Web (`test/boundaries.test.ts`).
* **`target`** takes the factory `Web.run` builds (`Web.target` with `container`, `primitives` and `native`) and returns the one it mounts or hydrates with, so a wrapper no longer has to give up `Web.run`'s duties (the `Mounted`, the URL policy, `stop`). It is the unprotected hatch: what it writes to DOM the PORT owns is not kept true. `docs/use/platform.md` now shows both, `native` first.

Additive: a `Web.run` call without them is unchanged. Tier 3 (an explicit escape hatch to the platform), Web only, not in contract v1. Test: `examples/todo/test/native-hatch.test.ts` (and PORT Web's own tests of the hatch). Audits for the Valance column: **H1** (a documented way down) ◐, unchanged: of the two reasons the 10-25 validation gave, one is gone ("`Web.run` takes no target": it now takes one) and one stays (the hatch reaches the Web only; the desktop host builds its own target, and a desktop parallel waits for evidence, Port ROADMAP §2.8). The refinements plan expects H1 → P from B6; that disagreement is recorded for the owner. **H2** (the hatch cannot corrupt framework state) ◐ to P: `native`, the hatch the docs now lead with, gets no report or dispatch, and the PORT re-asserts its slots (tested in PORT). `target` stays unprotected by design and is marked so; the 10-25 validation scored H2 on the weaker documented hatch, and on that reading `target` alone would keep it ◐ (recorded for the owner, not resolved here).

**Upgrading.** Nothing is required. Before the release this branch installs PORT Web from a local pack (a `DO NOT MERGE BEFORE THE RELEASES` commit); the release raises the `@valancex/port-web` ranges to PORT's release with the hatch.
