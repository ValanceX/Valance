# VALANCE v0.4 release notes

## v0.4.0

*Prepared 2026-10-05. Not yet released: a pushed `v0.4.0` tag publishes it (see `.github/workflows/release.yml`), after review.* A minor release of `@valancex/valance`. It makes writing an application shorter and its types more precise, adds application-owned startup work, documents (and tests) how asynchronous work is owned, and moves to the MESH 0.9 / NEXUS 0.10.3 / PORT Web 0.2.4 dependency set. Existing applications keep working; the few type-level changes to watch are under [Upgrading from 0.3.0](#upgrading-from-030).

### Why a minor

Before 1.0 a minor version is a new range. 0.4.0 adds public API (`start` in the definition, name-keyed commands, a no-input `command` form, an exported `CommandTable` type) and changes the generic signature of `define`, which can affect code that spelled its type arguments out.

### Commands: shorter to write, precise in their types

- **Name-keyed commands.** A command table key without a `/` is a command's *name*. VALANCE binds it to every `component/name` a view declares with that name, and to `app/name` (for `invoke`, history and `start`). One definition serves every view that raises it:

  ```ts
  commands: (state) => {
    const command = Valance.command(state);

    return {
      increment: command((current) => ({ ...current, count: current.count + 1 })),
      add: command(Schema.Struct({ amount: Schema.Number }), ({ amount }, current) => ({ ...current, count: current.count + amount })),
    };
  },
  ```

  An exact `component/name` key still wins over a bare name, so a view can override one. A struct command takes the event's arguments **by position, in field order**. Exact keys and `Valance.entry` behave exactly as before.
- **No-input commands.** `command((current) => next)` is a command that takes nothing: the same command as `command(Schema.Struct({}), (_input, current) => next)`.
- **`Valance.entry` is the advanced adapter**, for when an event's arguments need adapting before they become a command's input (or one command is bound under an exact key). It is no longer the thing every application starts with.
- **Failures keep their own types.** `define` reads the command table's own type, so commands that fail differently (each with its own error) share one table, and `E`/`R` are the union of what the table can fail with and needs. `CommandValidationError` is part of it, since every command validates its input. The exported `CommandTable` type names the table's shape.
- **The state type comes from the schema.** `state.initial` no longer drives inference (`NoInfer`), so a literal in `initial` cannot narrow or widen the type the schema declares. This needs **TypeScript 5.4 or newer** in the application.

### Application-owned work

- **Startup work.** `define({ start: "app/load", … })` (or the bare name `"load"`) names a command the application runs once, as the last step of `start`, owned by the application from the moment it is admitted. It reads the state `start` was given (hydration included), may finish before anything is mounted (a later mount draws the settled state), and a key the table lacks fails `start` with the typed `UnmappedCommand`. During `renderToHtml` it begins too.
- **Asynchronous work is an ordinary command that waits.** Once admitted (by `invoke`, a mount's event, or `start`) it belongs to the application: closing a mount does not end it, closing the application interrupts it and awaits it before the runtime terminates, and a result that arrives after the close changes nothing. Commands run concurrently and VALANCE has no notion of an older request: drop a stale result with a ticket kept in the command's closure. Loading, success and failure are state the command commits. [Async work](../learn/async-work.md), [Startup work](../learn/startup-work.md) and [Contract §18](../V1_CONTRACT.md#18-asynchronous-work-and-start-time-work) cover this, with the evidence.

### Rendering and updates

No behavior change: a mount presents committed state as a latest-state consumer, the same view is an `update` and another view a `draw`, and `hydrate` adopts server markup. This release adds **evidence** for what a view can do through the whole stack in a real browser: conditional branches appear, disappear and swap in place, keyed list items keep their DOM node, typed input value and event routing through insert, remove and reorder, and both compose with application-owned async work and its cancellation. (Conditional and repeated structure is MESH's provisional `mesh-if` / `mesh-each`; their spelling is MESH's decision.)

### Compatibility set

| Package | Range | Role |
|---|---|---|
| `@valancex/nexus` | `^0.10.3` | dependency of `@valancex/valance`, and an application-level direct dependency. Its MESH runtime is a peer, so there is one runtime |
| `@valancex/mesh-runtime` | `^0.8.0 \|\| ^0.9.0` | peer, required; the one runtime NEXUS, PORT Web and VALANCE share |
| `@valancex/port-web` | `^0.2.4` | optional peer, for `@valancex/valance/web` and `@valancex/valance/web/server` |
| `effect` | `^3.10.0` | peer |
| `@valancex/mesh-compiler` | `^0.9.0` | build time only |
| `@valancex/valance` | **0.4.0** | the commit this tag will point at |

Run against both runtime lines (0.8.0 and 0.9.0) on the published dependency set. Declare the runtime yourself (`pnpm add @valancex/mesh-runtime@^0.9.0`): with NEXUS 0.10.2 or earlier, whose runtime was a hard `^0.8.0` dependency, an application on MESH 0.9 got a second runtime that a browser's `init()` never reached.

### Upgrading from 0.3.0

- Install `@valancex/nexus@^0.10.3` and `@valancex/port-web@^0.2.4`, and add `@valancex/mesh-runtime` to your own dependencies (`^0.9.0`, or stay on `^0.8.0`).
- If you wrote `define<S, E, R, V>(…)` with explicit type arguments, drop them: the signature is now `define<S, T, V>` and `E`/`R` are derived from the commands table.
- `StartError` is wider by `UnmappedCommand` (a `start` key the table lacks). An exhaustive `switch` over its `_tag` needs one more case.
- Use TypeScript 5.4 or newer.
- Optional: replace one-line `Valance.entry(command, …)` wrappers with named commands; nothing requires it.

### Known limits

- `start`'s outcome is not reported anywhere (no caller, no ledger): work whose failure should be seen commits it as state.
- Only Chromium is driven by the browser tests.
- In a browser, call the MESH runtime's `init()` before `start`, as since 0.3.0.

- A clean external pnpm project on the published packages installs one MESH runtime, and NEXUS, PORT Web and VALANCE resolve the same module.
