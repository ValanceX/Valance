# VALANCE v0.1 release notes

## v0.1.0

*Prepared, not yet released: the tag, the date and the npm publication follow the maintainer's tag.* This is the first release of `@valancex/valance`. It is the validated architectural baseline: the package as it stands at the Stage 56 architectural checkpoint (see [`docs/FINDINGS.md`](../FINDINGS.md), "Architectural checkpoint" and "Canonical lifecycle architecture"), after the 0.0.1 tracer bullet grew into a real page running in Chromium. It changes nothing in NEXUS, MESH or PORT.

### What it is

- **Entries:** `.` (`define`, `start`, `mount`, `hydrate`, `ApplicationHandle` = `{ state, invoke }`, `Mounted`, `Target`, `TargetFactory`, `Report`), `./web` (`target`, `history`), `./web/server` (`renderToHtml`), and `./internal` (the composition protocol for binding authors and tests; unstable by design).
- **Lifetimes:** the application lives in the caller's `Scope` (NEXUS, one state, the command registry, platform resources; shutdown closes admission, drains admitted commands, terminates NEXUS, releases resources last). A mount lives in the caller's own `Scope`; the two are unrelated unless the caller relates them. A command admitted from a click is the application's once admitted. `Mounted.dispatched` and `settled` are mount-owned diagnostic and synchronization facilities.
- **Validated end to end** (MPRX to MESH compile to NEXUS to render-v1 to PORT Web to the real DOM and back): SSR and hydration, keyed updates, in-place browser history, startup failure, a genuine back/forward-cache restore, and the built page served by an ordinary Node process, all in real Chromium.
- **Evidence at the baseline:** 30 package unit tests, 182 jsdom tests, 29 Chromium tests, 4 built-page smoke tests and 1 real-bfcache test, typecheck and build clean.

### Not in this release (still unproven, by design)

A second PORT, a real asynchronous browser capability, data that ages, long-lived pages, several mounts in a real browser page, browsers other than Chromium, consumption by an external project, and server-side commands. They are listed in the checkpoint and should be taken up when a real requirement appears.

### Notes

- The package is pre-1.0: the API can still change.
- Bundling for the browser with Vite reports that `@valancex/mesh-runtime` references `node:fs/promises`; the browser path (WASM loaded with `fetch`) works, as the built-page tests show.
- Release automation follows NEXUS, MESH and PORT (`.github/workflows/release.yml`): after this is merged, pushing the tag `v0.1.0` runs all of CI on the tagged commit, packs `@valancex/valance`, publishes it to npm with provenance (it needs the `NPM_ACCESS_TOKEN` secret, as the other repositories do) and creates the GitHub release with the tarball and these notes. A pull request that changes the workflow or the package version runs the same steps as a dry run.

## Post-0.1.0: the V1 development line

*Unreleased. This section describes what has changed in the repository since the 0.1.0 baseline above; it is not a release, carries no version or date, and does not change what 0.1.0 was.* The 0.1.0 section above describes the baseline as it was and stays as written; where this section differs, this section describes the current behavior.

The reader-facing contract for this line is [`docs/V1_CONTRACT.md`](../V1_CONTRACT.md).

### Behavior changes in `@valancex/valance`

- **Latest-state presentation.** A mount presents committed state as a latest-state consumer: a woken follower reads the current state and may skip superseded intermediate states, and a state it already presented is not presented again. Application commits are authoritative and never wait for a mount. This replaces the 0.1.0-era behavior in which every commit was rendered in turn; statements in `docs/FINDINGS.md` that say otherwise are historical.
- **`mount` / `hydrate` settle instead of hanging.** Into a Scope that is already closed, or that closes before the follower starts, they end with the Scope's interruption.
- **A throwing `unmount`** no longer leaves a closed mount holding its dispatches: `Scope.close` fails with the target's defect, but VALANCE's own bookkeeping is released, so `settled` on a closed mount returns at once.
- **`Web.history`** logs a defect in the application's `urlOf` or `stateOf` and ends only that synchronization step, instead of ending the follower.

### Contract and documentation

- `docs/V1_CONTRACT.md` is the new reader-facing contract. `docs/CONSTRAINTS.md` remains the engineering constraints and tripwires (extended with the lifecycle, command, state, observation and capability boundaries), and `docs/FINDINGS.md` the historical investigation record.
- Capability and resource ownership (acquired by `start`, held across consumer closes, released once with the application's Scope, never reached after close) is established and tested; it needed no code change.

### Validation on this line

- Package unit tests: 34 passed (5 files).
- Workspace jsdom tests: 414 passed (57 files).
- Chromium (`pnpm test:browser`): 47 passed (17 files), over 12 consecutive full runs including shuffled file order. One browser test was changed for isolation (a probe left a forward entry in the shared session history); no product change.
- Typecheck and build clean.
- The built-page smoke tests and the real-bfcache test were not part of this validation run.

### Not changed

The public entries, `ApplicationHandle` (`{ state, invoke }`) and the compatibility set are as in 0.1.0. The package is still pre-1.0.
