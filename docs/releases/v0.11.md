# VALANCE v0.11 release notes

## v0.11.0

*Released 2026-10-14 as v0.11.0 (npm: `@valancex/valance`, `@valancex/common`, `@valancex/cli`).* A minor release of three packages that share one version and are published together, in this order:

| Package | Is | Stability |
|---|---|---|
| `@valancex/valance` | The composition boundary over NEXUS, MESH and PORT | Stable, as before |
| `@valancex/common` (new) | What an application's `src/main.ts` imports (`defineApp`, `component`, `field`), and the runtime a built application runs | **Provisional** |
| `@valancex/cli` (new) | The `vlx` command: make, serve, build, check, sync and extend an application | **Provisional** |

**`@valancex/valance` itself changes in no API and no behavior**: an application that changes nothing behaves as before. It takes the minor so that the three packages have one version and one tag (`v0.11.0`, [`release.yml`](../../.github/workflows/release.yml)); `@valancex/common` and `@valancex/cli` depend on `^0.11.0` of it. Before 1.0 a minor is a new range.

### What `vlx` is

`vlx` is the way into Valance: it makes an application (`vlx init`), serves it as you edit (`vlx dev`), builds the static site (`vlx build`), checks it (`vlx check`), refreshes the generated files (`vlx sync`) and adds to it (`vlx generate`). An application is Markdown content, a layout, components and styles; the project writes no compiler step, manifest, server, hydration script or bundler configuration. The root README starts there, and [`packages/cli/README.md`](../../packages/cli/README.md) is the guide.

### `@valancex/common`

- **The authoring API moved out of the command line package.** `src/main.ts` imports `defineApp`, `component` and `field` from `@valancex/common`, and `Schema` from `effect`. `Schema` is no longer re-exported.
- **The runtime a built application runs moved with it.** The browser and server entries the build generates (`@valancex/common/client`, `/server`), the content model, the routes, the scope a layout reads, the state and the tag table now live in `@valancex/common`; `@valancex/common/internal` shares them with the build tools. A built or deployed application depends on `@valancex/common` alone. `@valancex/cli` is a development tool: a new project has it as a dev dependency, and it no longer brings the terminal interface, Vite or the MESH compiler into the application's dependencies.
- It depends on `@valancex/valance`, `@valancex/mesh-runtime` `^0.11.0` and `@valancex/port-web` `^0.4.0`, with `effect` a peer. `@valancex/common`'s authoring entry has no Node, bundler or terminal import (a test checks it).

### Changes in the application model

- **`components` replaces `uses`.** A component is registered once, in `defineApp({ components: [...] })`. Which components a template uses is read from the template, so the per-component `uses` list, and its errors (`component-undeclared`, `component-unused`), are gone. A file under `src/` that is not registered is still `template-unused`. A registered component that no template writes yet is not part of the program, and is not an error.
- **Slots** (`<mesh-slot />`, `<mesh-slot name="…" />`, `<mesh-fill slot="…">`) work in components and are documented in the CLI guide.

### Commands

- **`vlx generate page <path>` and `vlx generate component <name>`** (alias `g`): add a Markdown page, or a component (`src/<name>.mprx`, `src/<name>.ts`) imported and registered in `src/main.ts`. Nothing is overwritten.
- **`vlx sync`** brings `.valance/` (the template types, the manifest, the entries) up to date and never fails. A new project runs it by itself after install (its `prepare` script) and before `typecheck`; `vlx generate` runs it after it writes; `dev`, `build` and `check` already did.
- **`vlx help [command]`**, and `--help` for every command.
- `vlx init` writes a `tsconfig.json` (it documented one and did not write it), so typed template imports and `typecheck` work in a new project, and it writes the new dependencies: `@valancex/common` and `effect`, with `@valancex/cli` as a dev dependency.

### The VS Code extension (not published)

*Later: it is published as **VALANCE for VS Code** 0.1.0, on its own tag (see the [v0.13 notes](./v0.13.md)).*

It runs the project's own `vlx check` by itself when a window opens and whenever a content, template, code or settings file is created, changed, deleted or saved, one run at a time, and tells the language server after each run, so nothing has to be run by hand first. The `valance.check.onType` setting, which was never implemented, is gone.

### Compatibility set

| Package | Range | Role |
|---|---|---|
| `@valancex/valance` | `0.11.0` | this release |
| `@valancex/common` | `0.11.0` | depends on `@valancex/valance@^0.11.0`, `@valancex/mesh-runtime@^0.11.0`, `@valancex/port-web@^0.4.0`; peer `effect@^3.10.0` |
| `@valancex/cli` | `0.11.0` | depends on `@valancex/common@^0.11.0`, `@valancex/valance@^0.11.0`, `@valancex/mesh-compiler@^0.11.0` |
| `@valancex/nexus` | `^0.12.0` (0.12.3 recommended) | dependency of `@valancex/valance` |

`@valancex/cli` and `@valancex/common` name MESH `^0.11.0`; `@valancex/valance` itself also admits MESH 0.12, and moving the tooling to 0.12 is a later release.

### Upgrading

- **From the workspace versions of the tooling** (none was published): replace `import { component, defineApp, field, Schema } from "@valancex/cli"` with `import { component, defineApp, field } from "@valancex/common"` and `import { Schema } from "effect"`; list every component in `components` and delete each `uses`; put `@valancex/common` and `effect` in `dependencies` and `@valancex/cli` in `devDependencies`.
- **From `@valancex/valance` 0.10:** change the version; nothing else.
