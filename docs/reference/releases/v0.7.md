# VALANCE v0.7 release notes

## v0.7.1

*Prepared 2026-10-10.* A patch release of `@valancex/valance`. It changes no behavior.

- **The `ApplicationDefinition.start` doc comment (it ships in the `.d.ts`) now says what the code does.** It said the start-time command's exit "is not reported anywhere"; a failure it does not catch is logged (`Effect.logError("start-time work failed", cause)`) with the whole cause, unredacted, as [API stability](../stability.md#what-is-logged) has said since 0.6.0. The comment now says so and tells you to keep secrets out of the errors such work lets escape. Found by validating the released set against the API design principles (§11, §14). Whether the log should carry the whole cause is a behavior of a stable surface, so changing it is a minor release's decision, not this patch's.
- **Use `@valancex/port-web` 0.4.1 or later.** `Web.link` (`<a href>`) wrote a `javascript:` URL from data as given; PORT Web 0.4.1 refuses such a URL (`unrealizable-value`) for every URL attribute. The peer range `^0.4.0` already admits 0.4.1; nothing in VALANCE changes.

## v0.7.0

*Prepared 2026-10-10 (not yet released: v0.6.0 is the latest release).* A minor release of `@valancex/valance`. Before 1.0 a minor version is a new range.

### Why a minor

It moves every substrate to a new minor (NEXUS `^0.12.0`, MESH `^0.10.0`, PORT Web `^0.4.0`) and changes how a later presentation reaches a target: only what changed is drawn.

### What is new

- **Only what changed is drawn.** A later render of the same view used to be a whole new tree that the target compared with the last one. It is now MESH's `update` of the render before: the runtime reuses everything the new state leaves alone and returns the `render-patch-v1` patches that turn the old tree into the new one, and the Web target applies them in place (`WebPort.patch`). The work is proportional to the change, and an element nobody changed (a text field being typed in, a focused control) is not touched. A view change still draws afresh, and a first presentation, including hydration, is still a whole render.
- **`Target.patch` (optional).** A target whose PORT can apply patches has `patch(patches)`; the composer gives it the patches of each later render of the same view. A target without `patch` is given `update(tree)` exactly as before, so a custom target keeps working. `Web.target` and `Web.run` already have it.
- **Composition without composite config.** With MESH 0.10, `compileProgram` infers the contracts of an application's composites and declares the reserved tags a program uses, so `manifest()` from `@valancex/valance/web/build` no longer needs the composites written next to it; named slots and `mesh-switch` are available to views. See the MESH 0.10 release notes. (`manifest()` itself is unchanged: it still derives the primitives, the root views and the commands.)

- **A grace for shutdown.** `start` (and so `Web.run`) takes `shutdown: { grace }`: closing the application waits up to the grace for the commands it admitted to finish before it interrupts what is left, and NEXUS 0.12 does the same for the work it tracks (`Runtime.run` and `runFork`) before resources are released. The default, `0`, is the behavior of 0.6: interrupt at once. New commands are refused throughout, with the same `admission-closed` defect.

### Compatibility set

| Package | Range | Role |
|---|---|---|
| `@valancex/nexus` | **`^0.12.0`** | dependency |
| `@valancex/mesh-runtime` | **`^0.10.0`** | peer, required |
| `@valancex/port-web` | **`^0.4.0`** | optional peer, for `@valancex/valance/web` and `/web/server` |
| `effect` | `^3.10.0` | peer |

### Upgrading from 0.6.0

- Move the three packages above together; the runtime peer no longer admits MESH 0.8 or 0.9, because NEXUS 0.12's `Mesh.update` needs 0.10's `update`.
- Nothing in an application has to change at run time. A custom `Target` keeps working without `patch`.
- In a browser the MESH runtime now loads its packaged module itself if `init()` was not called (MESH 0.10); where a bundler or a development server moves the module (Vite 5 to 7 prebundling), the error names `init()` and the `optimizeDeps.exclude` remedy.
- A hand-built target typed `TargetFactory<WebPort>` no longer typechecks, because `WebPort` (PORT Web 0.4) gained `patch`, `inspect` and `[Symbol.dispose]`: type it as `TargetFactory<HydratableTarget<HydrationResult>>`, the contract the composer needs, or add the members.
- A page that relied on every presentation re-asserting the DOM (a script that edits the DOM under the application) now sees an untouched element stay as it was; a controlled field is still reasserted when its rendered value changes.

### Validation

Against the packed 0.10.0 / 0.4.0 / 0.12.0 packages and this package's own pack, in a clean project and in this repository:

- Package: typecheck; 15 files / 123 tests (two new files: one pins the three presentation paths, patches to a target that has `patch`, `update` to one that has not, a fresh draw for another view; one pins `shutdown.grace`).
- Tracer: typecheck; Node 74 files / 548 tests; Chromium 25 files / 57 tests; smoke 4 tests. The work-count and render-supersession tripwires now count and gate MESH's `update` as well as `render`: a later commit costs one view evaluation, one scope and one **update**, never a full render, and the DOM changes only where something changed.
- docs-site: 4 tests and 2 Chromium smoke tests.
- docs-verifier: 22 tests and 2 Chromium smoke tests, which also compare the page after in-place navigation with the server's HTML for the same URL, and check that the page holds only elements its templates name (no wrapper spans or sections).
- The tracer's two tripwires on the substrate route `Application.shutdown(running.nexus)` now pin NEXUS 0.12's behavior: the admitted command is interrupted before the resource is released (0.11 released it under the command).
- One `@valancex/nexus`, one `@valancex/mesh-runtime` and one `effect` resolve in a clean `npm install` of the five packs.
