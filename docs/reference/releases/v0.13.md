# VALANCE v0.13 release notes

## v0.13.0

*Prepared 2026-10-15 (nothing tagged or published: v0.12.0 is the latest release).* A minor release of four packages that share one version and are published together, in this order: `@valancex/valance`, `@valancex/common`, `@valancex/cli`, `@valancex/router`. The VALANCE extension for VS Code is released separately (below). Before 1.0 a minor is a new range.

**In short:** one application can now be built for the web and for a native desktop window from the same state, commands and content (`vlx init --web --desktop`); navigation, text-field keys, stored state, color schemes and links out of the application are modelled once and realized by each target; the router owns navigation; and the editor has a published extension.

| Package | Is | Stability |
|---|---|---|
| `@valancex/valance` | `Native.run`, the engine side of a native window, beside the web's `Web.run` | Stable; `native` is **Provisional** |
| `@valancex/router` | `History`, the list of places visited, and the guard kind `"history"`; `permit` | **Provisional**, as before |
| `@valancex/common` | Targets, `derived`, `persist`, `Store`, `Open`, `appearance`, `guard`, navigation (`back`, `forward`), the portable core of the web vocabulary, and the desktop entry | Provisional, as before |
| `@valancex/cli` | Desktop and multi-target projects, `vlx generate target`, `vlx package --desktop`, one language-server settings file per target | Provisional, as before |
| VALANCE for VS Code (`valancex.valance` 0.1.0) | MPRX templates, project checks and connection lenses, one language server per target | **Provisional**; tag `vscode-v0.1.0` |

`@valancex/common`, `@valancex/cli` and `@valancex/router` depend on `^0.13.0` of `@valancex/valance`; `@valancex/common` also depends on `@valancex/router` and `@valancex/port-web` `^0.6.1`, and `@valancex/cli` on `@valancex/port-desktop-vocabulary` `^0.6.0` (PORT 0.6, already released).

### One application, more than one target (new)

One definition built into a web site and a native window. The Desktop PORT's window is built from its source until the PORT is published; everything here is **Provisional** (see [API stability](../stability.md)).

- **One project, more than one target (experiment).** `vlx init --web --desktop` makes a project with both settings files; `defineApp({ targets: { web: { layout, components }, desktop: { layout } } })` gives each target its templates while the state, the commands and the content stay one. `vlx build` builds every target (`dist/web/`, `dist/desktop/`) or the ones named (`--web`, `--desktop`); `vlx dev` serves one at a time. The web vocabulary gains `checkbox` and `textfield`. The gaps it found are in `docs/explanation/application-model/multi-target.md`.
- **`vlx init --desktop` (new): the desktop target.** One target per project (`valance.desktop.json` marks it; the wizard now asks for one, and `--yes` means the web). Templates are checked against the Desktop PORT's vocabulary, with its own built-in layout and views, so a `<div>` is an error from `vlx check`. `vlx build` writes `dist/desktop/engine.mjs` (everything bundled) and `mesh-runtime.wasm`; `vlx dev` opens the PORT's `vlx-window` on it and opens it anew on each change. The engine's entry is `@valancex/common/desktop`.
- **`vlx generate target desktop`** adds a target to a project without moving anything: its settings file, and a layout of its own in `src/desktop/` registered in `targets`. `vlx dev` with no flag in a project of two targets serves the web and opens the window. Each target builds into `dist/<target>/`.
- **`@valancex/valance/native` (new): `Native.run`.** The engine side of a native application, as `Web.run` is for a page: `await Native.run(app, { titleOf, mayClose, onLink })` serves the application on stdin and stdout for the Desktop PORT's window. The window's title is the application's (`titleOf`), closing asks the application (`mayClose`), a link is an address the application interprets (`onLink`), and the application's log goes to stderr because stdout is the protocol. Contract §20.
- **Breaking, in `@valancex/cli`: the site is built to `dist/web/`.** `vlx build` wrote a one-target web project's site to `dist/`; every target now builds into `dist/<target>/` (`dist/web/`, `dist/desktop/`), so adding a second target moves nothing. Point a deploy step, a preview or a test that serves `dist/` at `dist/web/`. `vlx generate target` no longer needs to say so.
- **The Desktop PORT's vocabulary comes from its package.** `@valancex/cli` depends on `@valancex/port-desktop-vocabulary` and no longer carries a copy (`vocabularies/` is gone). `Native.run` takes `onNavigate` for the window's Back and Forward (Alt+Left, Alt+Right, the mouse's buttons; unmapped keys on macOS), and the desktop entry runs the framework's `back` and `forward` for it.
- **`vlx package --desktop`** packs the desktop engine into one executable (Node's single executable application, the MESH runtime inside) beside the Desktop PORT's window program, in `dist/package/<platform>/`. Linux x64 and Windows x64 (the other platform's `node` and window program are given with `--node` and `--window`). **Unsigned.** `--archive` also writes the package as one file, a `.tar.gz` (Linux) or a `.zip` (Windows), with its SHA-256 beside it; the archives are written without a clock or an owner, so the same files are the same bytes.
- **Images on the desktop.** A content image whose address is a file in `public/` is drawn in the window (PNG, JPEG, GIF, BMP, WebP), named by its description; `vlx build --desktop` and `vlx package --desktop` ship `public/` beside the engine. SVG, network addresses and missing files are drawn as their description.

### Navigation (new)

The router owns navigation; a page, a window and a phone each realize it with what they have (`docs/explanation/application-model/navigation.md`).

- **Navigation belongs to the router (`docs/explanation/application-model/navigation.md`).** `@valancex/router` exports `History` (the list of places visited and its moves: `start`, `push`, `replace`, `go`, `canGo`, `restore`), the guard kind `"history"` (the application moves along a list it keeps itself) and `permit` (runs a guard; one that fails refuses). `defineApp` keeps its `trail` and `cursor` with `History`, and takes an optional `guard` (the router's `Guard`) that is asked before `go` (`"programmatic"`), `back` and `forward` (`"history"`): `false` stops the move, `redirect(page)` sends it elsewhere. `persist: ["navigation"]` keeps the pages visited between runs where the engine keeps them (a window; a page's list is the browser's, and the address is the truth); a stored page that no longer exists is dropped and an empty list starts at the first page. `@valancex/common` now depends on `@valancex/router`.
- **`back`, `forward`, `canGoBack` and `canGoForward`.** The framework keeps a trail of the pages visited (`trail`, `cursor` in the state): `go` adds the page it goes to after the one shown, `back` and `forward` move along the trail, and a layout reads `canGoBack` and `canGoForward`. The desktop layouts have Back and Forward buttons. `trail`, `cursor`, `back`, `forward`, `canGoBack` and `canGoForward` are now names an application's own state, commands and scope cannot use.

### State, commands and the platform

- **`command.effect`: one way to write a command.** `Valance.command(state)` (and the `command` a `defineApp` gives) now has three forms: a pure transition (`command(next)`, `command(Schema, next)`), one that waits (`command.waiting`), and one whose body is an Effect (`command.effect(run)`, `command.effect(Schema, run)`): several steps, the state read between them, the router, a capability, a typed failure. An application no longer needs `Nexus.Command.define` or its own helpers; found by the to-do app, which had written a `define` and a `change` of its own. Additive: `Nexus.Command.define` and `entry` still work.
- **`derived`, and the portable core on the web.** `defineApp({ derived: (derive) => ({ open: derive(Schema.Number, (state) => ...) }) })` gives a template values worked out from the state, with their types, on every target. The web vocabulary gains `column`, `row`, `heading` and `text` (with `button`, `checkbox` and `textfield`: the Desktop PORT's names, props, events and payloads), props a template may leave out (a `button` needs neither `class` nor `pressed`), and a layout stylesheet for `column` and `row`; a component written with only these runs on both targets. Additive: the web's own tags stay. A stylesheet in `src/desktop/` is not loaded by the web.
- **`Store`, and `persist`.** A `Store` capability (`@valancex/common`: `Store.get`, `Store.set`, `Store.remove`; values go in as JSON and come out decoded by the Schema the caller states), supplied by the page (`localStorage`) and by the desktop (a file in the user's data directory). `defineApp({ persist: ["items", "theme"] })` keeps the named state fields between runs on every target: loaded when the application starts, saved when they change, what no longer fits ignored. `Native.run` takes a `platform`, as `Web.run` does.
- **`Open`.** A capability for sending a person to an address outside the application (`Open.open`, in `@valancex/common`): the page's is a new tab, the desktop's the system's own opener. Only `https:`, `http:` and `mailto:` addresses are opened. A link in a desktop window to an address elsewhere now opens in the person's browser.
- **`colorScheme` and `appearance`.** The system's colors are framework state, as the window's size is: a layout reads `colorScheme` (`"light"` or `"dark"`), kept current by the page (`prefers-color-scheme`) and by the desktop window (a `scheme` message), through the framework's `colorScheme` command. `defineApp({ appearance: (state) => state.theme })` asks the desktop window to look `light`, `dark` or `system` (an `appearance` message; the default is the system's). `colorScheme` and the command are now names an application's own state and commands cannot use.
- **`submit`, Enter in a text field (desktop).** The Desktop PORT's `textfield` has a `submit` event: the person pressed Enter in it. PORT Web can realize an event by one key; the web `textfield` gets `submit` when that PORT Web is released.
- **`cancel` on a text field.** Escape is the event `cancel` beside `submit` (Enter), on the web and in a window; a template writes `on.cancel={...}` once for both. Needs `@valancex/port-web` 0.6.1 (the range is now `^0.6.1`), which accepts two events of one primitive on the same DOM event type when different keys make them.

### `@valancex/router`

- `History` (`start`, `push`, `replace`, `go`, `canGo`, `restore`) is the list of places visited and its moves, pure and serializable; the guard kind `"history"` is for an application that keeps its own list (a window); `permit` runs a guard (one that throws or fails refuses). Not yet: nested routes, a `beforeunload` guard, a mobile adapter.

### `@valancex/common`

- `defineApp` gains `targets`, `derived`, `persist`, `appearance` and `guard` (above); `Store`, `Open` and `Navigation` are capabilities; `@valancex/common/desktop` is the entry a desktop build runs; the web vocabulary gains the portable core and `checkbox`, `textfield`.

### `@valancex/cli`

- `vlx init --desktop`, `vlx init --web --desktop`, `vlx generate target desktop`, `vlx dev` serving the web and opening the window (the window starts the engine again in place when a file changes), `vlx build [--web] [--desktop]`, `vlx package --desktop`.
- `.valance/editor.json` lists every target, so the editor can run one language server for each.
- The Desktop PORT's vocabulary is read from `@valancex/port-desktop-vocabulary`, not from a copy in the package.

### VALANCE for VS Code (separate release, `vscode-v0.1.0`)

The first published version of the extension (`editors/vscode`; id `valancex.valance`; VS Code 1.90 or later). It highlights `.mprx`, and, with the project's own `@valancex/mesh-lsp` and `vlx`, gives diagnostics with fixes, hover, completion, go to definition, formatting, the project's `vlx check` findings as problems (run by itself on open and on change), connection lenses above each prop, event, component use, state field and command, Find All References, and settings-file validation. For a project of several targets there is **one language server per target**, each with that target's components; a template two targets share is answered once. It ships as one bundled file, and the host tests run that bundle in a real VS Code. Its own changelog: `editors/vscode/CHANGELOG.md`.

### Also in this release

- `LICENSE` (MIT) is now in the repository, and so in every package tarball: the packages already said MIT, and their tarballs had no license file.
- `vlx package --archive` writes the package as a reproducible `.tar.gz` or `.zip` with its SHA-256 (no clock and no owner in the bytes, so the same files are the same checksum). Unsigned.

### Upgrading

- **From 0.12:** change the versions. `@valancex/common` now depends on `@valancex/router`.
- **The site is in `dist/web/`, not `dist/`.** Point a deploy step, a preview or a test that serves `dist/` at `dist/web/`. Nothing else about the build moved.
- **New names are the framework's.** `trail`, `cursor`, `canGoBack`, `canGoForward` (state a layout reads) and the commands `back`, `forward`, `persist`, `colorScheme` cannot be used by an application's own state or commands, as `page`, `go`, `viewport` and `resize` could not already; a project that used one gets a definition error that says so.
- **`@valancex/valance`'s optional peer `@valancex/port-web` is `^0.6.1`** (it was `^0.4.0`); a project on an older PORT Web gets a peer warning. A web table that gives two events of one primitive the same DOM event type, each made by a different key (Enter and Escape on a field), is accepted from 0.6.1 and was refused before.
- **The desktop target** needs the Desktop PORT's window, `vlx-window`, built from its source (`cargo install --git https://github.com/ValanceX/Port valancex-port-desktop --bin vlx-window`) until the crate is published; it is unsigned, and runs on Linux and Windows.
- **Node 22 or newer**, as before.
