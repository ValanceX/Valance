# VALANCE v0.15 release notes

## v0.15.0

*Prepared 2026-10-25 (nothing tagged or published: v0.14.0 is the latest release).* A minor release of the five packages that share one version and are published together, in dependency order: `@valancex/valance`, `@valancex/style`, `@valancex/router`, `@valancex/common`, `@valancex/cli`. Before 1.0 a minor is a new range. It needs the same MESH (0.15 or later), NEXUS (0.14 or later) and PORT Web lines as 0.14; nothing in MESH, NEXUS or PORT changes.

**In short:** components and themes can be installed from npm. A library marks itself with an export condition; an application that installs it configures nothing; `vlx init library`, `vlx library build` and `vlx library check` are the author's loop. A component's props and events are checked at the tag; a library that does not support a target gives one diagnostic at the use. Nothing in 0.14 code changes.

### Libraries ([guide](../../how-to/libraries.md))

Tiers, by the design north star:

* **Tier 1, using a library: nothing to configure.** `npm install acme-ui`, list its `components`, write its tag. `vlx check`, `build` and `dev` find it by what its `package.json` says (the `valance` export condition), compile its templates with yours, put its stylesheets in `@layer vlx-library`, and check its props and events where you write the tag.
* **Tier 1, making a library:** `vlx init library <name>` writes a workspace (the library, a playground that depends on it the way a consumer does, one layout per target); `vlx library build` writes `dist/` (JavaScript, declarations, templates and stylesheets as source); `vlx library check` holds the package to what a consumer's build relies on and builds the playground for each target the package declares.
* **Tier 2, when a name is taken:** a library component has the qualified id `package/name`. Two components of one tag are a compile error naming both ids; `defineApp({ resolve: { tag: "package/tag" } })` says which one the tag means; `override` replaces a built-in or a library component with your own. A package declares `targets` (default both) and `styles`; `kind: "theme"` makes it a theme package, named in `valance.json` (`"theme": "<package>"`).
* **Tier 3:** none added. `override` and `escape.web.css` are as before.

Mechanism that stays behind the boundary: marker discovery, the Vite conditions and `ssr.noExternal`, the removal of a component from a target that lacks it, and the library layer. `packages/cli/test/boundaries.test.ts` fails if the discovery module imports anything but Node's, and the reference library's `tests/boundary.mjs` fails on any import that is not a documented entry point.

### Fixes the reference build found

Each has a test that fails without it.

* `unit()` accepted no command made with parameters under strict TypeScript (F3).
* A `controllable` unit field was also a scope name and the component was refused (`manifest-unit-clash`) (F4).
* The web realization required class hooks on `paragraph`, `blockquote`, `list`, `olist`, `image` and `link` that the specification calls optional (F5).
* `vlx library build` shipped files of a component that had been renamed or removed (F6).
* `vlx init library` wrote workspace scripts that could not find `vlx` (E5), and no `allowBuilds` for pnpm 11 (F1).

**Findings for the owner** (reported, not shipped quietly):

1. *Smart-UI risk:* `vlx library check` needs `vlx library build` first because it checks `dist/`; the author drives the order. `check` could build to a temporary directory. Not done: the check of the real `dist/` is the point, and a stale `dist/` is the thing it must find.
2. *I2:* `resolve` is stringly typed. A typed id needs the library's types in the consumer, which K7 does not generate.
3. *Accessibility:* a disclosure and tabs are a `button` and `toggle`s, because the portable core has no `aria-expanded` or tab roles (K22).
4. *C1:* a library cannot receive a value from an ancestor without props; the architecture-sinkhole anti-pattern is not addressed by this release.

No change matches the entity-trap anti-pattern: a library's contract is its `component()` props and events, not its internals.

## Upgrading

* **From 0.14:** change the versions of the five packages together. Nothing is required: libraries are opt-in.
* A project that has a `theme/` directory and also sets `"theme"` in `valance.json` is refused (`theme-conflict`); that setting is new, so no 0.14 project has it.
* A library component named like a built-in (`heading`) is a compile error that names both ids; before, the first one silently won.
* A library linked from outside the project (`npm install ../acme-ui`) is not supported (`library-peers`); install a packed tarball or develop it in a workspace.

## Release steps (the maintainer's)

1. Merge when CI is green. The branch carries no local packs: the commit "DO NOT MERGE BEFORE THE RELEASES" was reverted on it.
2. Tag `v0.15.0`; `release.yml` publishes the five in dependency order.
3. `npm view @valancex/valance@0.15.0 @valancex/style@0.15.0 @valancex/router@0.15.0 @valancex/common@0.15.0 @valancex/cli@0.15.0 version`.
4. Create `ValanceX/Components` and `ValanceX/ecosystem-ci` from `reference/` (`git subtree split --prefix=reference/components`), run `pnpm install` in `components/` (it writes the registry lockfile), then `pnpm dedupe`, and commit the lockfile. Run the `ecosystem-ci` workflow with `tag: 0.15.0`.
5. In an empty directory: `npm install -g @valancex/cli && vlx init library acme-ui && cd acme-ui && npm install && npm run build:library && npm run check:library`.
6. Mark these notes "released" and update `scripts/measure-footprint.mjs` (`PUBLISHED`) to 0.15.0.
