# Implementation plan

*Written 2026-10-17 from the fifteen briefs, [decisions](decisions.md) and the research in [evidence](evidence/README.md). It turns the designs into work packages for implementation sessions. Everything here is a plan for work not yet done; nothing in it has been built except the footprint harness.*

## How an implementation session works

1. **Read, in this order:** the [front page](README.md) (fixed points, gates, the free window), the brief for the bet you are building, its rows in [decisions](decisions.md), and the scripts in [evidence](evidence/README.md) that back its numbers.
2. **One work package at a time**, on its own branch, in small commits. Every package ends in the **acceptance check** listed for it, and the check is run, not described.
3. **Build to stage 3** (a prototype behind a marked namespace on one target, measured against the budgets). A bet moves to stage 4 only when two targets realize it and the reference build uses it from outside; record that in the bets index.
4. **Verify against specifications** (fixed point 10): the verifiers in [Bet 7](bets/accessibility.md) are the gate for emitted output. A browser, bundler or screen reader that disagrees with a specification is not our bug.
5. **Keep the free window honest.** Anything may break until the Reference Gate passes, but a break names its replacement in a diagnostic (X4).
6. **Update the documents with the code:** a decision that turns out wrong is changed in `decisions.md` with the date and the reason; a new measurement goes into a new dated file under `baselines/`, never into an old one; a friction report goes to the bet's brief.
7. **Do not create pull requests unless asked, and push only to your session's branch.**

## Ground rules that apply to every package

- The ten fixed points in the front page bind. In particular: no arbitrary code in views (1), checked before it runs (2), nothing dropped silently (6), data only on every wire format (8), start-up carries only what start-up needs (9), output verified against specifications (10).
- Dev builds are silent about size; production builds minimize (W9, W10).
- A new diagnostic has a stable code and a suggestion where one exists.
- A new conformance vector is data, written before the implementation it covers (U6).

Findings that need a decision are recorded in [the new baseline](baselines/2026-10-17-vlx-build.md) (a second WebAssembly runtime in a plain install, and WebAssembly memory still growing after 1,000 updates) and below:

- The limits of G5 apply to every MPRX source, not only generated UI: a file over 64 KB is `input-too-large`. A 64 KB source holds at most about 4,600 elements of 14 bytes, so the 5,000-element limit is reached only by short elements.

**WP0 review and consolidation (2026-10-18).** The three code branches and the docs branch were reviewed, merged into `claude/optimistic-gates-9xmvhs` of each repository (the `scripts/measure-footprint.mjs` conflict resolved in favor of the code branch's version) and the checks re-run. Review found the work sound; notes and follow-ups:

- **The WebAssembly memory growth has a cause and a fix.** Valance never called `release()` on the render an `update` replaces, and the runtime keeps that render until it is released: 1,000 updates took a counter from 2.31 MB to 4.63 MB without it and left it at 2.31 MB with it. `connect` now releases the previous render, with a test that fails without the change (W21). **Follow-up (WP8):** re-run the harness's memory rows with the fix before the memory ceilings gate, and check the JavaScript heap row the same way.
- **A second WebAssembly runtime ships in a plain install** (432 KB transferred against 261 KB). Decision W20: one `mesh-runtime` range across `common`, `valance` and `nexus`, and a production `vlx build` that fails naming both copies. **Follow-up (WP0b):** align the peer ranges and add the guard.
- **`blockquote` joins the role set** (23 names, A11); the Desktop PORT still has to set `Role::Blockquote`. **Follow-up (WP0b).**
- **Nits for WP0b:** in the Desktop list, the bullet or number is drawn as its own label inside each `ListItem`, so an assistive technology reads "bullet" before the text; mark the marker as decoration or give the item the text alone. The new `template-builtin` error is a break for any application that names a component like a built-in without `override`; it is documented in the CLI README and is inside the free window.
- **The G5 limits apply to every MPRX source**, and the time budget per push is not built. **Qualified override ids** (K14) remain a TODO at the collision site.

## WP2. Language (MESH)

In this order, each ending at stage 3 with vectors in Rust and JavaScript (the Language Gate needs stage 4).

1. **[Bet 4](bets/variant-types.md): `enum`, `has`, `??`, `default` on props** (T1 to T13). New codes `unknown-variant`, `manifest-enum-too-large`, `manifest-duplicate-variant`, `redundant-presence-test`, `redundant-default`; no new runtime code; no string joining. *Acceptance:* the codes are in the diagnostics manual; the equivalence law (`update` equals `render`) still holds on all vectors; `evidence/language/replay.mjs` still gives equal hashes.
2. **[Bet 5](bets/template-values.md): snippets** (U1 to U14): `{#snippet}`, `{@render}`, a snippet kind, `children` reserved, render step `0x08`, `template-v2` emitted only where used and `v1` still read, caps 512 and 64. Slots become sugar and are retired after the Language Gate. *Acceptance:* identity vectors for the render step are written first; recursion over a tree fails closed at the cap.
3. **[Bet 10](bets/collections.md): the `window` clause and `len`** (L1 to L14), plus the `scroller` primitive's tree fields. *Acceptance:* 10,000 rows windowed to 50 render in at most 35 ms with a tree of at most 12 KB (`evidence/language/floor.mjs`); a scroll step from the changes form takes at most 2 ms.
4. **`ref` kind** for node references (A12) belongs here because it is a manifest kind. *Acceptance:* `unknown-ref` on a reference to nothing.

**WP2 step 1 status (2026-10-18, third implementation session).** Done, on `claude/wp2-enum` of `valancex/mesh`. `enum`, `has(x)`, `x ?? y` and `default` on props are implemented through the manifest, checker, `template-v1` (a compatible addition: the expression `has` and the operator `coalesce`), runtime and docs, with the codes the step names and no new runtime code. Evidence: the existing conformance programs render byte for byte as before (their manifest is untouched); `replay.mjs` gives the same hashes on the published 0.13.0 packages and on the new ones; a new vector directory `examples/conformance/enums/` (own manifest) passes in Rust and JavaScript; a test installs 0.13.0 and shows an enum is `manifest-unknown-kind` there. Not done, as scoped: the Valance Effect Schema bridge (T7) and editor hover or completion for enum values. The Port's pin stays on the WP1 commit; it should move to the new Mesh commit when it adopts the `enums/` vectors.

**WP2b status (2026-10-18, fourth implementation session).** Branches: `claude/wp2b-template-v2` of `valancex/mesh` (template-v2 and snippets) and `claude/wp2b-bridge` of `valancex/valance` (T7 and the W24 measurement).
(1) **W24: the 3,000-update run did not finish because of the harness, not the product.** Every update cost the harness about one second across seven browsers and three builds (a `setTimeout(0)` wait is clamped to 4 ms by the browser, and the unthrottled and 4x runs each pay it); the cost per update is flat from 200 to 3,000 (see [the new baseline](baselines/2026-10-18-w24.md)), so there is no superlinear cost to fix. The loop now waits with a `MessageChannel`, and `--runs` and `--only counter` bound a run. The baseline holds the 200, 1,000 and 3,000 figures, whether the heap is flat past the ledger's bound, and the recomputed ceilings.
(2) **T7 (Valance side) is done.** A `Schema.Literal("a", "b")` or a union of string literals becomes the manifest kind `enum`; number and boolean literals keep their kinds; any other union that has no MESH type is a diagnostic at the field's line in `main.ts`; `field(schema, default)` writes the manifest `default`. The cli probes the installed `@valancex/mesh-compiler`: one older than 0.14 cannot read `enum` or `default`, so `vlx` widens an enum to `string` and refuses a default with a message naming the version; the end-to-end test that an enum prop's literal is checked at the use site (`unknown-variant`) runs only against a compiler that reads enums.
(3) **U15 is done:** `template-v2` is a superset of v1; the compiler writes it only for a template that uses `has`, `??` or snippets (every other template is byte for byte what it was, with the same fingerprint, tree and keys, which `replay.mjs` shows with the same hashes on the published 0.13.0 and on this tree); the runtime reads both; v1's schema no longer allows `has` or `coalesce`, and a v1 document that holds them is malformed. Published 0.13.0 reports `assembly-unsupported-format-version` for a v2 document (a test installs it).
(4) **Bet 5, stage 3 in MESH.** `{#snippet name(a, b)}…{/snippet}` and `{@render name(args)}`; the manifest kind `snippet` for composite props and scope names; `children` as the reserved snippet prop; contravariant parameters with exact arity; lexical scope; recursion capped at 64 levels (`runtime-snippet-depth`); identity step `0x08`; the memoization hazard is a failing test without the guard; vectors in Rust and JavaScript (`examples/conformance/snippets/`). Slots are untouched. Not done: `{@render}` as a composite's root (U13): the grammar rejects a render tag as the whole document (`syntax-error`, "a render tag cannot be the document"), so a composite cannot yet be written as a pure forwarder; LSP has hover and definition for snippet names only (no completion); the Valance `component()` side for snippet props. The compiler's gzipped WebAssembly is 321,522 bytes with snippets, so W23's budget is now 330,000 (recorded in `decisions.md`).
