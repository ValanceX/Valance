# Baseline, 2026-10-17, built with `vlx build`

The second baseline, written by the first implementation session (work package 0). The [first one](2026-10-17.md) bundled the counter with esbuild; `vlx build` uses Vite, and the two differ by a factor of two in JavaScript (decisions W15 and W16, and the bundler erratum in the first file). This one measures what an application built with the tooling gets. The first file is not edited; the ceilings of decision W3, which were provisional until this existed, are recomputed [at the end](#ceilings-recomputed-w3).

Measured by [`scripts/measure-footprint.mjs`](https://github.com/ValanceX/Valance/blob/claude/wp0-defects-housekeeping-k4q5kt/scripts/measure-footprint.mjs) on the branch `claude/wp0-defects-housekeeping-k4q5kt` of `valancex/valance` (until it is merged, it is not on the default branch).

## How it was measured

| | |
|---|---|
| **Packages** | Installed from npm on 2026-10-17 into temporary directories: `@valancex/cli` 0.13.0, `@valancex/common` 0.13.0, `effect` 3 (resolved to the newest 3.x), and what they pull in. `@valancex/mesh-runtime` 0.12.0 and `@valancex/port-web` 0.6.1 are what npm resolves (see [installability](#installability-and-a-second-webassembly-runtime)). The update benchmark uses `@valancex/mesh-runtime` and `mesh-compiler` 0.13.0 directly |
| **Applications** | **The counter**: one layout, one number, one command, one page, `vlx build --web` (a project of 4 files, in the harness). **`docs-app`**: the `examples/docs-app` of this repository (3 pages, a layout, a theme toggle), `vlx build --web`, against the published packages. Both are server-rendered by `vlx build`: the page has its text before any JavaScript runs |
| **Environment** | A Linux container, 4 vCPUs, 16 GB, Node 22.22.0, Chromium 141.0.7390.37 (Playwright's build 1194, driven with `playwright-core` 1.56.1 and the DevTools protocol), no network throttling, served precompressed over localhost. One machine; wall-clock numbers are for it only |
| **Sizes** | Raw, gzip (level 9) and brotli (default quality) of each file `vlx build` wrote under `dist/web/assets/` |
| **Browser** | Median of 7 fresh contexts per row, with and without Chromium's 4x CPU throttling. The least of two harness runs is shown for every millisecond row; sizes and bytes were identical in both |
| **Memory (W18)** | After the application is interactive, the JavaScript heap and WebAssembly memory are read; then a fixed number of updates (200) is made by clicking the button, a garbage collection is forced, and both are read again. WebAssembly memory is the sum of the `WebAssembly.Memory` objects the runtime's module exports, found by wrapping `WebAssembly.instantiate*`. The renderer's resident set is reported, not gated |
| **Update** | The least of 10 (render) or 15 (update) runs |
| **Reproduce** | `PLAYWRIGHT_MODULES=<a node_modules with playwright-core> CHROMIUM=<the chrome executable> node scripts/measure-footprint.mjs --json results.json` (add `--updates N`, `--pages N`, `--skip-browser`, `--keep`) |

Development runs of the harness are not reported: the earlier ones generated pages that were too alike, which is the first entry under [what this measurement got wrong first](#what-this-measurement-got-wrong-first). The numbers below are from the last two runs of the final harness (`--updates 200`), plus one run with `--updates 1000` (its sizes were the same; only the memory rows use it).

What `vlx build --web` writes for the counter, with the packages deduplicated to one `@valancex/mesh-runtime` (the case the ceilings are set from):

|---|---:|---:|---:|

| `mesh-runtime.wasm` | 765,371 | 232,170 | 170,828 |
| CSS | 126 | 102 | 80 |
| Transferred by the browser, all files, brotli | | | 260,671 (261,005 at 4x) |

`docs-app` (3 pages), same packages:

| What | Raw | gzip | brotli |
|---|---:|---:|---:|
| JavaScript (2 chunks) | 410,525 | 106,734 | 92,708 |
| CSS | 1,781 | 793 | 634 |
| `mesh-runtime.wasm` | 765,371 | 232,170 | 170,828 |

Cross-check: the same `docs-app` built in the workspace, which the first baseline's erratum measured, has a client entry of 410,264 bytes raw and 92,576 brotli; this build's is 410,237 and 92,550, so the harness and the workspace build agree to 0.01 percent in size.

**Bytes per added page (W17).** 20 generated pages (about 1.3 KB of Markdown each, each with its own text drawn from a list of 40 words) were added to `docs-app`, taking it from 3 pages to 23. The client JavaScript grew by **2,471 bytes raw, 333 gzip and 267 brotli per page**, and the number of chunks stayed at 2. Page content is compiled into the client entry, so the client's size grows with the number of pages, as W17 noted (about 1.8 KB per page in the first estimate, from smaller pages).

The ecosystem's share of the JavaScript was not re-derived here: that needs a source map (`evidence/measurement/smap.mjs` does it), and the first baseline's figure for a real `docs-app` build (Effect 75 percent) stands.

## Start-up and interaction (Chromium, localhost)

The page is server-rendered, so "first paint" is now the browser painting HTML and no longer measures the application; the figure that does is **interactive at**, the time until a click is handled (a click made earlier does nothing: [Bet 14](../bets/resumable-start.md)). The harness clicks every 10 ms from the start of the page until one registers, so the figure has about 10 ms of granularity plus one click.

| Counter, deduplicated | No throttling | 4x CPU |
|---|---:|---:|
| First contentful paint | 44 ms | 124 ms |
| Interactive at | 189 ms | 779 ms |
| So the dead zone is about | 145 ms | 655 ms |
| One click to the updated DOM | 7.6 ms | 40.5 ms |

Not comparable with the first baseline's "first paint of `Count: 0`" (211 ms), which was a client-rendered page that showed nothing until the JavaScript ran; the comparable figure is interactive at.

## Memory after updates (W18)

Counter, deduplicated, unthrottled, medians of 7 browsers. The JavaScript heap is after a forced garbage collection; WebAssembly memory is what the runtime's module holds.

| | At start | After 200 updates | After 1,000 updates |
|---|---:|---:|---:|
| JavaScript heap | 5,347,156 | 4,410,264 | 5,031,672 |
| WebAssembly memory | 1,310,720 | 4,653,056 | 11,337,728 |
| Renderer resident set (reported) | | about 150.5 MB | about 162.5 MB |

Two things stand out. **WebAssembly memory is not at a plateau after 200 updates.** It was 3.6 times its starting value after 200 and 8.6 times after 1,000 (and the 1,000 figure varied between 10.8 and 11.6 MB across browsers). Decision W18's note that it "plateaus near 1.8 times the start value" does not hold for this counter. WebAssembly memory cannot shrink, so growth is expected up to the most the application ever holds at once, but a counter that holds one number holds the same tree at update 1,000 as at update 1: this is either allocator fragmentation or something retained per update, and the data here cannot tell which. The JavaScript heap, after collection, is 0.6 MB higher at update 1,000 than at 200. The gate in W18 (a fixed number of updates) is still sound, but its number, and the claim that the memory settles, need a longer run and a look at what the client and the runtime keep per update. Under 4x CPU throttling the WebAssembly figure is less repeatable (4.46 to 4.65 MB at 200 updates), so only the unthrottled figure is used below.

## Installability, and a second WebAssembly runtime

Unchanged from the first baseline: the newest set does not install together. npm resolves `@valancex/mesh-runtime` 0.12.0 (newest 0.13.0) and `@valancex/port-web` 0.6.1 (newest 0.9.0).

**New: the resolved set contains two copies of the runtime, and a build ships both.** `@valancex/valance` 0.13.0 accepts `mesh-runtime` `^0.11.0 || ^0.12.0` and gets 0.12.0, while `@valancex/common` 0.13.0 depends on its own 0.11.0. `vlx build` bundles both WebAssembly files (764,239 and 765,371 bytes) and the browser fetches both:

| Counter | JavaScript brotli | WebAssembly brotli | Transferred, brotli | WebAssembly memory after 200 updates |
|---|---:|---:|---:|---:|
| As npm resolves it | 88,086 | 341,787 (two files) | 432,064 | 5,767,168 |
| Deduplicated to one (`overrides`) | 87,918 | 170,828 | 260,671 | 4,653,056 |

A plain install is 171,393 bytes (66 percent) heavier to transfer than it needs to be. The workspace build of the same example has one copy (the first baseline's erratum and the check above), which is how the duplicate stayed hidden. The ceilings below are set from the deduplicated build; the duplicate is a **known red** beside installability, with the same root cause (peer ranges that lag the newest packages), and would be fixed by one `mesh-runtime` range across `common`, `valance` and `nexus`.

## What this measurement got wrong first

- **Pages too alike.** The first run of the bytes-per-page measurement added 20 pages with the same text and reported 31.7 brotli bytes per page, because brotli compresses a repeated page to almost nothing. The raw figure was right and the compressed one was a fiction. The fix, a generator for different text per page, was itself wrong: it took the low bits of a linear congruential generator, which repeat, so each page used six words, and it reported 156 bytes. With the high bits the figure is 267 bytes. It is still a floor, since 40 words compress better than prose; **the raw figure (2,471) is the one to gate.** A check of the distinct words per page would have caught the second mistake at once.
- **A flat start-up.** The counter now arrives as HTML, so its first paint is 44 ms whether or not the application works. A page that never started would have passed. The harness stalls, with a 60-second limit, if a click never registers, and reports interactive-at as well.
- **Two WebAssembly files.** The first thought was a harness fault. It is real, and is in the section above.

## Ceilings recomputed (W3)

Rule of W3: the baseline plus 5 percent, rounded up to the next 100 bytes (the next 10 for a figure under 1,000), then ratcheted down. The ceilings of the first baseline for the esbuild-bundled counter (JavaScript 170,300, transferred 350,400) are retired: that was a hand-bundled application, not one built with `vlx build`. None of these is enforced yet; the harness reports and does not fail (the release check is work package 8).

| Metric | Baseline | Ceiling |
|---|---:|---:|
| Counter JavaScript, brotli | 87,918 | **92,400** |
| `mesh-runtime.wasm`, brotli | 170,828 | **179,400** (unchanged) |
| Counter transferred, all files, brotli (the larger of the two throttle rows) | 261,005 | **274,100** |
| `docs-app` JavaScript, brotli | 92,708 | **97,400** |
| Client JavaScript per added page, raw | 2,471 | **2,600** |
| Client JavaScript per added page, brotli | 267 | reported, not gated (depends on the text) |
| JavaScript heap after 200 updates | 4,410,264 | **4,630,800** |
| WebAssembly memory after 200 updates | 4,653,056 | **4,885,800** |
| First contentful paint, interactive at, click, update, render (ms) | as above | ratio gates: 2x the previous release (1.5x for `update`), on one machine |
| Wire, 1,000 rows, one changed item | 185,924 | none yet (**known red**) |
| Newest set installs together, and one WebAssembly runtime in the install | no, and no | must pass at release (**known red**) |

The two memory ceilings should not gate until the growth above is understood: a ceiling set on a number that is still moving would be a ceiling on the length of the run.

## Limits

One machine, one browser, localhost only, unthrottled network. The counter and `docs-app` are small; the bytes-per-page figure is for pages of about 1.3 KB of Markdown, and a page with a table or many links will cost more. The 200-update and 1,000-update memory figures are for a counter, whose tree is one number. The harness installs the published packages, so a change in the working tree is not measured until it is released or packed.
