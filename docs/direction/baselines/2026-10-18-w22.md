# Baseline, 2026-10-18, the bounded ledger (W22)

The fourth baseline. The [third](2026-10-18-working-tree.md) found the JavaScript heap growing about 150 bytes per update, retained through `Mounted.dispatched`. W22 bounds that record to the most recent 1,000 exits. This file measures the working tree with `scripts/measure-footprint.mjs --tree` at 200 and at 1,000 updates, and recomputes the heap ceilings. The earlier files are not edited.

## How it was measured

As in the third baseline: the workspace's `cli`, `common`, `valance` and `router` packed with `pnpm pack` and installed as tarballs beside the published `mesh-runtime` 0.12.0, `nexus` 0.12.3 and `port-web` 0.6.1; the counter and `docs-app`, both `vlx build --web`; Chromium through `playwright-core`, JavaScript heap after a forced collection, WebAssembly memory summed over the exported `WebAssembly.Memory` objects; medians of 7 fresh browsers, with and without 4x CPU throttling. The tree is commit `215e73c` of `claude/wp2-ledger`. Two runs, `--updates 200` and `--updates 1000`. Wall-clock rows are not reported: both runs shared the machine with test suites.

## JavaScript heap after a forced collection (unthrottled, median of 7)

| | At start | After 200 | After 1,000 | Third baseline: after 200 | Third baseline: after 1,000 |
|---|---:|---:|---:|---:|---:|
| Counter | 5,369,220 | 4,423,536 | 5,028,040 | 4,406,024 | 5,023,808 |
| `docs-app` | 4,750,248 | 4,674,428 | 5,205,032 | 4,657,116 | 5,201,076 |

Under 4x throttling the figures are within 0.5 percent (counter 4,423,472 and 5,007,420; `docs-app` 4,673,236 and 5,028,828).

**Is the heap flat after warm-up? Not shown by this table, and it could not be.** With a bound of 1,000, the ledger still holds every exit at 1,000 updates, so the 1,000-update heap is the same as before the change (5,028,040 against 5,023,808, within 0.1 percent), and it should be: the bound has not yet dropped anything. The change only shows past 1,000 updates, and a run of 3,000 updates on the same harness had not finished when this was written (the 1,000-update run took over an hour on a shared machine). What does show it is the logical measurement: `examples/tracer-web/test/event-retention.test.ts` (group G) sends 1,005 events and finds exactly 1,000 exits kept and 5 counted as dropped, with a bound of 3 keeps 3 of 5, and with `0` keeps none. The growth found by the heap snapshot of the third baseline was one `Exit` and a few small objects per update, all retained through this array and nothing else, so with the array bounded the growth stops at the bound's size: about 140 bytes times 1,000, which is the 600,000 bytes between 200 and 1,000 updates in the table. **A browser measurement at 3,000 or more updates is the missing evidence, and a gate on the 1,000-update heap waits for it.**

WebAssembly memory is unchanged and flat: counter 1,310,720 and `docs-app` 2,228,224 bytes at start, after 200 and after 1,000 updates.

## Ceilings recomputed (W3, W18)

Rule of W3: the baseline plus 5 percent, rounded up to the next 100 bytes. Not enforced yet (WP8). The sizes and the WebAssembly memory are as in the third baseline (this change touches no bundle size that the harness reports: `mesh-runtime.wasm` is 765,371 bytes raw, 170,828 brotli, as before).

| Metric | Baseline | Ceiling |
|---|---:|---:|
| Counter JavaScript heap after 200 updates | 4,423,536 | **4,644,800** (was 4,626,400) |
| `docs-app` JavaScript heap after 200 updates | 4,674,428 | **4,908,200** (was 4,890,000) |
| Counter JavaScript heap after 1,000 updates | 5,028,040 | would be 5,279,500; not gated until the run past 1,000 shows it flat |
| `docs-app` JavaScript heap after 1,000 updates | 5,205,032 | would be 5,465,300; not gated until the same |

The 200-update ceilings rise by 0.4 percent because the heap at 200 is 0.4 percent higher than in the third baseline (the new code in `connect`, and run-to-run difference between builds); both stay under the third baseline's ceilings plus that amount. The WebAssembly ceilings of the third baseline stand.

## Limits

One machine, one browser, one run each. The flatness past the bound is argued from the retention path and the logical test, not measured in the browser (see above).
