# Baseline, 2026-10-17

What the published packages cost to ship, start and update, measured with [`scripts/measure-footprint.mjs`](../../../scripts/measure-footprint.mjs). The numbers are the starting point for the [budgets](../bets/budgets.md). A later baseline is a new dated file; this one is not edited.

## How it was measured

| | |
|---|---|
| **Packages** | `effect` 3.22.3, `@valancex/mesh-runtime` 0.12.0 (and 0.13.0 for the update benchmark), `@valancex/mesh-compiler` 0.12.0, `@valancex/nexus` 0.12.3, `@valancex/valance` 0.13.0, `@valancex/port-web` 0.6.1, installed from npm into a temporary directory |
| **Application** | The counter from [Your first application](../../tutorials/01-first-application.md): one view, one number, one command, bundled for a browser with esbuild (minified, tree-shaken, ESM) |
| **Environment** | A Linux container, Node 22.22.0, Chromium 1194 through Playwright 1.56.1. One machine. Wall-clock numbers are for this machine only |
| **Sizes** | Raw, gzip (level 9) and brotli (default quality) bytes. Brotli is what a modern host sends, so it is the figure that matters |
| **Browser** | Median of 7 fresh contexts, served precompressed over localhost. "First paint" is the time until `Count: 0` is in the DOM. The 4x row uses Chromium's CPU throttling |
| **Update** | The least of 10 (render) or 15 (update) runs, as the repository's own `bench-update.mjs` does, because noise only adds time |
| **Reproduce** | `node scripts/measure-footprint.mjs --json results.json` (add `--runtime 0.13.0` to benchmark another runtime, `--skip-browser` without Playwright) |

## Installability

`@valancex/valance@0.13.0` accepts `@valancex/port-web` `^0.6.1` and `@valancex/mesh-runtime` `^0.11.0 || ^0.12.0`. The newest published versions are `port-web` 0.9.0 and `mesh-runtime` 0.13.0. Consequences measured:

- Installing the packages without pinning succeeds, and npm picks `mesh-runtime` 0.12.0 and `port-web` 0.6.1: **two of six packages are behind the newest**.
- Asking for `@valancex/port-web@0.9.0` explicitly next to `@valancex/valance@0.13.0` fails with `ERESOLVE`.

Package sizes as published (unpacked): `mesh-runtime` 866 KB, `mesh-compiler` 962 KB, `valance` 241 KB, `nexus` 163 KB, `port-web` 170 KB, `common` 127 KB, `cli` 296 KB.

## Findings

1. **Size is a dependency story.** Effect is 83 percent of the JavaScript. The ecosystem's own code is small.
2. **Effect's barrel import costs about 45 KB raw for nothing.** `import { Schema } from "effect"` pulls `fast-check` and `pure-rand` through Effect's property-testing module, and the subpath `effect/Schema` does not (318 KB against 176 KB in the single-import test). Aliasing those two packages to an empty module in the full counter bundle saves 45,911 raw, 14,102 gzip and 12,431 brotli bytes (7.7 percent of the JavaScript, 3.7 percent of the total transfer). NEXUS and Valance import from the barrel, so the saving needs a change to their imports, not to applications.
3. **The obvious WebAssembly optimization makes transfer worse.** `wasm-opt -Oz` shrinks the file by 22 percent raw (765,371 to 599,472) and **grows** it compressed: gzip +4.6 percent, brotli +9.9 percent (170,828 to 187,722). The build already uses `opt-level = "z"`, LTO, `strip` and `panic = "abort"`. Gate on compressed bytes, not raw.
4. **A browser bundle needs help.** `@valancex/mesh-runtime` loads `node:fs/promises` dynamically for Node, and esbuild stops on it unless told `--external:node:fs/promises`. The runtime's own error text points at the equivalent for Vite. It is an authoring-cost entry for the cognitive-load log.
5. **Start-up is not dominated by compute.** First paint is 211 ms unthrottled and 847 ms at 4x CPU for 333 KB of transfer, so on a real network the bytes will matter at least as much as the CPU.
6. **The Desktop protocol's update cost scales with the tree, and the patches already exist.** At 1,000 rows it sends 920 times the bytes of the patch list.

## What this measurement got wrong first

Recorded because the budgets will be only as good as the harness.

- The first browser number was 3.5 seconds, nearly unchanged under CPU throttling. A flat number under throttling meant a wait, not compute. The harness was compressing every request at maximum brotli quality. Compressing once up front gave 211 ms. The harness now does that, and the lesson is a rule: **a new metric gets a sanity check before it is believed**.
- The first reading of installability said the newest set fails to install. It does not: npm backtracks to older compatible versions. The check now compares what npm picked with the newest published version.

## Limits

One machine, one browser, localhost only. No other framework was measured, so nothing here says whether 333 KB is large or small for a counter. That comparison would use this same harness on a counter in other stacks.

## Errata (added 2026-10-17 by the consistency pass; the measurements above are unchanged)

- Finding 1: the ecosystem's own packages are 58,066 of 607,655 bytes, which is 9.6 percent (the text said about 9).
- Finding 2: the roughly 45 KB (45,911 bytes raw, 12,431 bytes brotli) is the measurement of `fast-check` **and** `pure-rand` together (the alias). `fast-check` alone is 36,654 bytes raw and `pure-rand` 8,890.
- The 7.7 percent figure for the same saving is of the brotli JavaScript (12,431 of 162,138); in raw bytes it is 7.6 percent (45,911 of 607,655).
- The gzip +4.6 percent for `wasm-opt -Oz` has no source row in the tables above; only the brotli +9.9 percent can be derived from them.
- "Wire bytes" are `JSON.stringify(...).length`, which counts characters, of the runtime's tree, not of the Desktop protocol's envelope.
- **The bundler (added after research the same day).** The counter was bundled with esbuild, as the harness does, not with `vlx build` (Vite). The same counter entry built with Vite 7 is 279,535 B of JavaScript (79,220 B brotli) and contains no `fast-check` or `pure-rand`, against 607,671 B (161,977 B brotli) from esbuild. The size, transfer and Effect-share figures above therefore describe a hand-bundled application, not a `vlx` one. The `docs-app` example built with `vlx build` has a client entry of 410,264 B (92,576 B brotli). Finding 2 applies only to esbuild bundles.
